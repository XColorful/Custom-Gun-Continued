# 方案 C：跨实例 draw 合并与实例化

> B1 之后，成本从「顶点数」变成「draw 数」。方案 C 处理的是下一步：**同一纹理的多个实例能不能合成一次 draw**。它不解决顶点生成（B 已经解决），只解决 draw 与状态切换的倍数。

## 定位

|项|内容|
|---|---|
|解决的大头|B1 之后残留的「每实例 × 每纹理一次 draw」|
|不能解决|动态实例的顶点生成（B1 已覆盖）；静态实例（B2 已覆盖）|
|成本模型|新：`Σ(不同网格 × 纹理)`，与实例数解耦|
|预期|multi 9 把：B1 后约 0.05–0.35 ms → **0.02–0.07 ms**（推算）|
|风险|GPU 实例化需要自定义顶点属性 / 着色器，光影兼容风险高|

## 三种做法

### C1 按纹理排序提交（无着色器，最稳）

`MultiBufferSource.getBuffer(renderType)` 在 RenderType 变化时会隐式 `endBatch` 上一个桶；逐模型提交时每把枪都会切一次纹理，等于每把枪都触发一次 flush。把一帧内所有枪的提交按 RenderType 排序后再写，可以让同纹理的顶点连续进入同一个桶：

- 去掉 `ModelObject.render` 的逐模型 `endBatch`；
- 收集所有实例的「纹理 + 顶点写入」后统一 flush；
- 同纹理的 N 个实例共用一次 draw。

代价：CPU 仍要为每个实例写一遍顶点（`O(N × V)`），只是省掉 N−1 次 draw 与状态切换。适合**动态实例**（多人第三人称、掉落物），不需要任何着色器改动。

### C2 世界空间合并（B2 的推广）

静态实例直接烘进同一份世界空间 `VertexBuffer`，一次 `bind + draw`，CPU 零成本。这是 multi 场景的终点形态，已在 [方案 B](./scheme-b-baked-mesh.md#b2静态实例的世界空间合并) 中描述；C 不重复。

### C3 GPU 实例化（收益最高，风险最高）

顶点数据只存一份，per-instance 矩阵作为实例属性或常量缓冲，一次 draw 画 N 个：

- 1.20.1 的 `VertexFormat` / `RenderType` 没有实例化通道，原版 entity shader 只读 `ModelViewMat`；
- 要实例化只能自建 `VertexFormat` + 自建 shader，这会绕过 `RenderType` 的材质与光影映射；
- 26.3 的 `VertexFormat` 有 `stepRate`（逐实例属性），但标准 entity 管线把模型矩阵烘进了顶点坐标，**同样需要自建管线**。

因此 C3 只适用于「动态实例数量大、且愿意承担光影兼容」的场景。按当前基准（multi 9 把、全部可见），C2 已经把静态部分压到 1 次/纹理，C3 的增量收益不足以抵消风险。

## 决策

|场景|B1 后的 draw/帧（推算）|推荐|
|---|---:|---|
|9 展示框（静态）|9–36|**B2**：合并后 4–7|
|多人第三人称|玩家数 × 纹理数|C1（排序提交）；实例数量大时再评估 C3|
|掉落物|数量 × 纹理数|C1；物品实体本身在旋转，不能走 B2|
|第一人称|纹理数 × 2（静态 + 脏子树）|不适用；它的 draw 已经很有限|

结论：**C 在静态场景被 B2 覆盖，在动态场景先用 C1，C3 作为远期备选**。这也符合 [总览](./Home.md#推荐路线) 把 C 排在阶段 4 的原因。

## 与光影的关系

- C1 不碰着色器，只改变提交顺序；`RenderType` 仍由原版 / Oculus 接管，风险与现状相同。
- C2 是 B2 的一部分，风险见方案 B。
- C3 需要自建管线；Iris / Oculus 下几乎必然需要单独的兼容层，且可能无法进入阴影 pass。**未验证**。

## 验收

|项|指标|
|---|---|
|C1|`endBatch calls` 降到「纹理批次数」；`endBatch flush` 总量下降；画面与提交顺序无关（透明枪除外）|
|C3|draw 数降到「不同网格数」；光影开 / 关画面一致；GPU 侧 draw 数用 mixin 统计|

透明枪不参与排序合并，保持原有提交顺序。
