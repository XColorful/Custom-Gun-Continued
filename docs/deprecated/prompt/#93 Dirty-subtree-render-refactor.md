## 实现要点

**分块拓扑（[ModelObject.java](core/src/main/java/dev/xcolorful/customgun/client/model/ModelObject.java)）**
- 顶层节点是块根，自身变换只进绘制矩阵——动画写根（bob / 后坐 / 跳跃）零重烘。
- 状态段逐节点比较 `stateHash()`，某节点首次变脏时在它所在的块上切开，之后只重烘它自己的子树；静态部分留在剩余大块里，稳态 0 重建。
- 块网格不含块根自身的变换与可见性，所以块根的状态变化全程免费；可见性 / 被替换渲染由绘制时的祖先链剪枝处理，被剪枝的块标脏、恢复可见时重建一次。

**单节点退回**
- `FunctionalBedrockPart` 在状态段按节点统计回调写入的顶点，命中的节点（内置只有 `MAG_ADDITIONAL`）整棵子树改为 `BufferSource` 即时绘制，换弹帧不再整模型退回即时管线。

**瞄具模板**
- [`_AttachmentModelRender.renderModelPart`](core/src/main/java/dev/xcolorful/customgun/client/model/_AttachmentModelRender.java:232) 把路径前缀提升为绘制矩阵，枪身骨骼动画不再让瞄具网格逐帧失效。

**退回与生命周期**
- 无着色器时用 `StaticBake.available()` 在状态段之前退回（回调不会执行两次）；分块网格挂在模型上、由 `StaticBakeCache.clearAll()` 统一释放，跨光照（光影阴影 pass）每块保留最多 4 份。

## 二、b1-b-1 设计取舍

- **不要 multi**：展示框/地面/第三人称走整模烘焙，动画不会切块，测试 1 测不到它们；光影下 B1-a 已在 `26.35.11.1-4` 验证过（23.9 → 7.19 ms），不必重测。multi 若加进来只会增加进程噪声。
- **ak47 + 满配 m4a1 两把，不要裸配**：ak47 节点最少、脏子树占比最高（p99 53%），切块最激进，是「膨胀 / 原模型」最坏的一组；满配是目标场景且 draw 最多（43 次）、含瞄具模板。裸配在这两者之间，信息增量小。
- **一点基线污染**：进档时的装备动画可能已经切过块，所以「换弹前」是装备动画之后的状态，测试量的是换弹**额外**引入的 draw。标准里已写明，报告里要按这个口径解释。

## 三、b1-b-2（光照）要点

- **预期先摆在这**：MC 的光照是离散值（block light 0–15），手持枪的光照采样点跟着玩家走，移动时只在**跨过亮度边界的那些帧**重建，不是持续重建。每秒走一格 ≈ 每秒最多一次全模型重建（0.1–0.6 ms 的尖峰），平均占比不到 1%。所以「动态光照让优化全没」大概率不成立；测试要回答的是尖峰幅度和频率。
- **需要一个小调试任务**（仿 `DebugKeyReloadTest`）：每 20 tick 前移一格、若干格后传回起点、10 s 后自动停止并保存。它和换弹测试共用 F12 会冲突，实现时要拆成两个模式或两个键。
- **建以 F12 一起跑**：`Bake rebuilds` / `Static bake` 是唯一能直接数出「光照触发了多少次重建」的探针（这次是真的需要，不算额外加探针）。
- **解耦三条路，按风险排序**：
    1. 提高每块网格的光照条目上限（现在 4 条）——最省事，只缓解不根治；

## 1. 随机的是什么

随机的是**模式顺序**，不是多场景混合：

- `attrib` 基准：六种属性模式（I2I / I4I / POINTER_PART / POINTER_ITEM / POINTER_CACHED / PRODUCTION）每轮重排；
- `batch` 基准：三条队列路径（immediate / ordered / batched）每轮重排；
- 每个模式画的是**同一场景、同一批对象、同一参数序列**。

所以场景级成本是共模的，在模式对比里会抵消；随机顺序只用来把时间漂移（JIT、温度、区块构建）分摊到各模式，不会把不同场景的噪声混在一起。

## 2. 45 帧预热远远不够（尤其按物品计）

- 不是「进游戏 45 帧后开始」：是**每个块**（模式 × 轮次）在几何捕获/上传完成后再预热 45 帧，然后采 120 帧，共 3 轮。
- 按调用次数算：234 个 part × 45 ≈ **1.05 万次** part 调用，刚过 C2 的 1 万次门槛；128 个物品 × 45 ≈ **5.8 千次** item 调用，**没到**。
- 高帧率下 45 帧只有几十毫秒（800 FPS ≈ 56 ms），第一个块基本是冷代码；3 轮 + 随机顺序只能稀释、不能消除。
- 他们的独立 GL 微基准是 3 个 JVM、每 JVM 2 s + 12 批预热，那部分没有这个问题；有问题的正是游戏内长测。

结论：游戏内数据能看「同一路径内的相对差异」，但不能当作 JIT 稳态下的绝对值；对比本项目「跨进程 + 预热到帧率稳定」明显更弱。

## 3. 只测模型 = 只测 CGC 的一小段；只测 CPU 不够

- `cpu_ns` 只覆盖 `tryDraw`：缓存查询、矩阵/光照上传、材质与属性设置、绑定、draw 提交与恢复。**不含**状态机、数据刷新、委托（配件/手臂/文字）、瞄具模板、`BufferSource` 的 flush/上传。
- `frame_interval` 是相邻事件间隔、包含整帧其余部分，只能做同会话内的 A/B 差，不能回答「占整帧多少」。
- 只有 CPU + `GL_TIME_ELAPSED`（含提交空闲），没有 GPU 利用率或 pass 计时。
- 用我们的数据量温度：满配第一人称 CGC 0.570 ms / 帧 1.330 ms，其中 Model render total 0.418（delegate 0.185 在内）、瞄具模板 0.189。模型提交只是 0.2 ms 量级的一段，**+3.69% 折合只有约 7 µs**，远低于帧时间噪声；而且在光影下 6.5–7.5 ms 的帧由光影包主导，CPU 侧的这点差异根本看不出来。

## 4. 光照解耦的收益：不重建几何，但不是零成本

- 是「纯光照变化**不重建几何**」：他们的判据写得很明确——只改光照时 `builds`／`submittedVertices` 应不变，`rangeBytes` 反映独立 UV2 上传量。
- 但仍有成本：世界批次要上传 4 B/顶点的 UV2 段；INSTANCE 路径每次 draw 都要设实例属性（他们微基准里 26–140 ns/draw）。实例属性那条路是「每次 draw 付一点」，不是「变化时才付」。
- 折算到 CGC：UV2 全量约 **43 KB（ak47）/ 140 KB（满配）**，对比现在一次全量重建 **0.6–9.1 ms**。所以它能消掉大部分尖峰，但仍不是免费；而且光影下我们仍必须写 `vaUV2`，uniform 方案不可行。

这四点已经补进 [reference-tacz-1.2.0.md](docs/architecture/client/render/refactor/reference-tacz-1.2.0.md) 的「参照实现的实验强度」和 TODO 的光照项（UV2 字节数按实测上传字节折算，之前写小了，已改成 43/140 KB）。

# 

## 结论

**光照解耦和 B2 是正交的**：它不是 B2 的前置条件，也不必等 B2 完成之后。SBM 那边也一样——光照解耦与合批是两套独立机制，只是可以叠在一起用。

## 为什么 B2 不依赖它

- **正确性**：把 light 烘进顶点对合并批次是对的，只是失效粒度更粗。
- **目标场景**：展示框的光照由框所在方块决定，玩家不改造环境（放/拆光源、开关门、方块更新）就不会变；B1-a 的 multi 实测 `Bake rebuilds = 0` 就是证据。所以 B2 用 baked light 不会被光照问题卡住。
- **代价放大但罕见**：合并成一次 draw 后，一个实例的光照变化会触发**整个批次**重建（9 把枪约 3.5 MB），比 B1 的「每实例网格」更贵。但触发条件很少，属于可接受的已知风险。

## 实现方式不止一种

关键约束：**一旦跨实例合并成一次 draw，就没有「每实例不同 light」的位置**——实例属性（divisor=1）只在每个实例各自一次 draw 时成立。所以能活到 B2 的只有逐顶点方案：

| 方案 | 适用 | 光影 | 说明 |
|---|---|---|---|
| **独立 UV2 流**（4 B/顶点，单独 buffer） | B1 + B2 | ✅ | SBM 的世界批次做法；合并 draw 也能用；光照变化只上传一段 UV2 |
| **交错缓冲内原地重写 uv2** | B1 + B2 | ✅ | 不改顶点布局，改动最小；uv2 跨步分散，需要 CPU 侧副本或逐顶点 patch |
| 实例属性（divisor=1） | 仅 B1（逐实例 draw） | 需属性槽兼容 | 合并后整批共享一个实例值 → 失效 |
| uniform + 自定义 shader | 仅无光影 | ❌ | 每 draw 一个常量；合并批次里不同实例不同光无法表达 |
| （缓解，非解耦）按光照值多缓存网格 | B1 | — | 现状的每块 4 条网格上限，只覆盖回访 |

## 建议的实施时机

1. **B2 照常先做，用 baked light**——目标场景光照静态，不阻塞。
2. **B2 建批次时顺手记录每个实例的顶点区间**（成本≈0）。这样将来做解耦时，可以只重写某个实例的 UV2 段，而不是整批重建；否则整批重来会吞掉 B2 的收益。
3. **第一人称的光照尖峰**如果要治，可以在 B1-b 上单独做「原地重写 uv2」，不需要等 B2，但优先级低于 B2。
4. 真要正式做解耦，选**独立 UV2 流**——它是唯一同时满足「合并 draw + 光影」的形态；实例属性只适合留在 B1 的逐实例路径。

## 问题重述

平均帧时间不是判据。`b1-b-3` 的关键数字是 **2.6–2.9 次/秒、单次 0.6 / 1.4 ms（无光影）、2.7 / 9.1 ms（光影）**：平均只占 0.4%–2.6%，但它直接决定 1% low / 0.1% low（满配+光影 55.2 vs 静止 118.5）。你说的「固定频率瞬时掉帧」正是这个量级——每约 350 ms 一次 9 ms 的帧，观感就是持续卡顿。而且 2.6–2.9 次/秒只是火把场景的下界；室内经过灯、窗、楼梯时采样点跨界的频率只会更高。B2 合并成一次 draw 后，一次光照变化会重建整个批次（9 把满配约 11 MB），所以布局必须在 B2 之前定下来。

## 两条路线

| | A 独立 uv2 流 | B 交错缓冲原地重写 |
|---|---|---|
| 光照变化 CPU（满配实测微基准） | 17 µs | 21–43 µs（另需一次性 63 µs 副本） |
| 光照变化 GPU 上传 | 4 B/顶点 = 43–140 KB | 全量 1.24–1.29 / 1.86 MB |
| 几何 / VertexBuffer 重建 | 消除 | 消除 |
| 光影下 9 ms 尖峰 | 大概率能消掉 | **不确定**，全量上传可能保留大部分停顿 |
| 26.3 延迟渲染 | 需第二 vertex binding，待验证 | 字节布局不变，较保守 |
| 实现风险 | 中（attribute 覆盖、小缓冲轮转） | 低 |

CPU 侧两者都只有几十微秒，**真正的差别在 GL 上传**。光影下 9.1 ms 无法用 1.86 MB 的带宽解释，大头是队列已满时的驱动停顿；这正是「B 是否有效」的未知项，所以原型第一步必须把烘焙探针拆成 `Bake emit` / `Bake buffer` / `Light update`，先确认 9 ms 的构成。

## 光影兼容性（1.20.1 已核实源码）

- `NEW_ENTITY` 的元素顺序里 UV2 是第 5 个 → attribute **slot 4**；Oculus 的 `IrisVertexFormats.ENTITY`（52 B）里 UV2 仍是 slot 4。
- `ShaderInstance` 按格式元素顺序绑定 attribute；Oculus 对 `ExtendedShader` 加 `iris_` 前缀但序号不变，shader pack 的 `vaUV2` 就是 slot 4。
- 所以方案 A 只需在 VAO 上把 slot 4 指向独立光照 VBO，**不需要改 shader、shader pack 或 cgccshader**。阴影 pass 用同一几何、换一份小光照数组即可；方案 B 则要两份全量副本或每 pass 重传。
- 26.3 的 `withVertexBinding` 在 API 上支持多流，但 `PreparedRenderType.drawFromBuffer` 能否分 binding 绑定、Iris 26.3 的 program 是否接受第二 binding，尚未验证——因此两条路线都保留，1.20.1 先落 A，B 作为回退。

数据完全吻合：
