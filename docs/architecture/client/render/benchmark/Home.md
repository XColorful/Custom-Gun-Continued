各批次的分工：

- `26.35.11.1` 回答**端间对比**——TaCZ 与 CGC、Forge 与 NeoForge、是否装加速渲染，以及 multi 场景下静态展示优化的差距。
- `26.35.11.1-1` 回答**内部构成与跨版本对照**——两端一次提交的 0.2–0.6 ms 花在哪一层；Afterburner 与内置探针同表对照，并给出探针开销与延迟渲染的差异。
- `26.35.11.1-1` 的 multi 数据采集于附加弹匣泄漏修复前（[报告 5.1](./26.35.11.1-1/测试数据计算报告.md)）。修复后的补充采集在同目录的 [`#91 additional-magazine-fix/`](./26.35.11.1-1/%2391%20additional-magazine-fix/)：两端各 2 次、只测 multi 场景中进游戏空手这一段，四次均为 4005 立方体/帧。此后的构建均包含该修复。
- `26.35.11.1-2` 回答**驱动侧与新的成本量纲**：一次 `endBatch` 里上传与 draw 各占多少、draw 次数与上传字节、渲染线程每帧分配、GPU 是否饱和。multi 的场景基线（9 个石头 + 9 个空展示框、无手持枪）已单独测在 [`multi-baseline/`](./26.35.11.1-2/multi-baseline/)：1.20.1 1174.3 ± 23.9 FPS（0.852 ms），26.3 901.7 ± 42.8 FPS（1.109 ms），结果并入本批次报告、不另建报告。该批次用目录内的 [`analyze_extra.py`](./26.35.11.1-2/analyze_extra.py) 先看新增指标，标准指标仍按 `26.35.11.1-1/analyze.py` 的口径统计。
  - 注意：本批次新增探针带来约 **0.06–0.09 ms/帧** 的固定开销（26.3 全步骤、1.20.1 除持枪外），空手场景约 7%、multi 约 1.3%；整帧 `GPU frame busy` 实测为帧时间的 99.4%–99.8%，它是 GPU 命令跨度而不是利用率，不能用来判定 GPU 余量。
- `26.35.11.1-3` 回答**满配枪械的成本与 draw 下限**：附件（瞄具 / 激光 / 握把 / 枪口 / 枪托）把单枪立方体数抬到 2.3 倍、每枪 draw 数抬到 9 次，瞄具模板成为第一人称最大单项（0.72 ms，36.8%）。
  - 本批 multi 用 9 个**满配**展示框，与上一批的 9 把裸枪**不是同一场景**（14.72 ms vs 5.45 ms），不可跨批比较。
  - 每端只有 3 次重复，1.20.1 第 3 次采集缺少「满配」一段（n=2）；空手场景的探针固定开销按无探针构建（0.8003 ms）估算仍约 0.048 ms/帧。
- `26.35.11.1-4` 回答 **B1-a 静态烘焙的阶段验收与 TaCZ 对照**：三端同场景、同 4 步、各 4 次；B1-a 之后 CGC 的静态展示与 TaCZ 1.2.0 同水平（空手 1.174 vs 1.106 ms，重构前为 4.9×），光影 A/B 为 23.9 → 7.19 ms。本批取代 `26.35.11.1` 的 TaCZ multi 数据（n=1、步骤顺序相反、ak47 可能未拆枪托）。
- `26.35.11.1-5` 回答 **B1-b 第一人称脏子树烘焙的阶段验收**：静止帧时间裸配 1.669 → 1.004 ms、满配 2.887 → 1.330 ms；换弹段 CGC −48%～−71%，`Bake rebuilds = 0`（拓扑在第一次换弹后收敛）。F12 只采换弹段，静止 CGC 由 Afterburner 同次相减得到。
  - 子批次 `b1-b-1`：换弹切块后静态待机只 +0.02–0.03 ms（约 2%）；换弹是脏集上界，拓扑饱和后不再增长。
  - 子批次 `b1-b-2`：光影下烘焙仍生效（满配 7.52 → 7.00 ms），但帧时间被光影包主导，ak47 的差值在噪声内；无光影 A/B 与本批一致。
  - 子批次 `b1-b-3`：光照变化不会让优化全没——平均 CGC 不变，跨亮度边界的那一帧回到重构前成本（0.6/1.4 ms，光影 2.7/9.2 ms），每秒 2.6–2.9 次；只有满配+光影肉眼可见（1% low 115.7 → 59.1，ak47+光影 138.2 → 136.7）。拆分实测：9.2 ms 的 94% 是 `Bake emit`，上传仅 0.49 ms——光照解耦的两条路线都能消掉尖峰，先做原地重写。
- `26.35.11.1-6` 回答 **B1-c-B 光照原地改写的效果**：第 1–5 次为只解耦分块路径的构建（1% low 59.1 → 97.5，残留 100% 是瞄具子网格），第 6 次补齐瞄具子网格后 `Bake rebuilds` 归零、1% low **130.5**（同场景静止 139.1）、一次光照变化 **9.2 → 0.68 ms**。三组构建的划分与判读见报告。
- `26.35.11.1-8` 回答 **静态展示与 TaCZ 的差额归因**：两端同批测空展示框基线后，差从 `26.35.11.1-4` 的 0.067 ms 修正为 **0.043–0.055 ms / 9 把（每枪 4.7 µs，1.4σ）**；新增 `Static status` 探针把 CGC 每提交的 31.78 µs 全部闭合（状态段 13.89 + 数据刷新 2.94 + 2 次 draw 等 14.94）。差额小于任何单项，**与 B1-c-A 无关**，状态段去重只对「同款重复展示」有效（按 B2 标准不加入）。

## 约定

- 每个批次目录自带 `analyze.py`，运行后重新生成该批次的图；报告中的数值均由脚本计算，不手工录入。
- **B1-b（`26.35.11.1-5`）之后**：第一人称不再经过即时遍历，`Geometry traverse` 无命中；`Distinct / Dirty nodes`、`Dirty cubes` 只统计即时块（附加弹匣）与即时管线，不能再当作脏比例的分母。分块路径的失效看 `Bake rebuilds` / `Static bake`。
- `analyze.py` 同时兼容 1.20.1 与 26.3 的字段名（`Model render total` / `Model submit`、`endBatch flush` / `Model flush`、`endBatch calls` / `Geometry submits`），26.3 批次可按同样方式（6 次重复 × 4 步 + 6 次 × 2 步）采集后直接复用。
- `26.35.11.1-3` 的 `analyze.py` 按「标准 3 步 + multi 3 段」分组：标准步骤按立方体数（0 / ≈750 / >1200）、multi 的手持段按同一文件内的立方体数秩区分裸配与满配；缺段（n<3）只打印不报错。
- 原始数据中的进程名必须过滤为 `javaw.exe`（Afterburner 会连启动器一起录制；官方启动器在后台未最小化会略微拉低帧数）。
- **采集约定（所有批次）**：单个数据文件 = **一次启动 Minecraft + 进入存档**；换文件即重启游戏并重新进档。因此「重复」是跨进程重复，文件之间包含 JIT / GPU 时钟 / 区块加载等进程级噪声，跨文件的绝对值不做精确比较，只使用同一次采集内的相对值。
- 内置探针的窗口比 Afterburner 略长（提前开始、延迟结束），对齐方式见各批次报告。
- 探针定义与埋点位置见 [渲染链路分析总览](../chain/Home.md) 的「测量与数据登记」。
- 单次会话的结论不作跨版本外推；跨版本对比只在同一批次内进行。
- 修复（`31c977d1a`）后的 multi 场景可直接用 `Cubes submitted` 判定是否再次泄漏：9 把**裸枪**展示框、进游戏空手时为 **4005/帧**（修复前泄漏时为 4554，每把 61）；9 把**满配**展示框为 **12 852/帧**（每把 1428，`26.35.11.1-3`）。
