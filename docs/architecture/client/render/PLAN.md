目前计划进行一次大规模渲染重构，以彻底解决渲染性能问题，并逐步实现 1.20.1-26.3 跨版本统一

## 整体流程与约定

本次重构涉及多个细分任务，允许通过多次对话推进，需遵循以下约定：
- 逐步实施与人工验收：渲染结果需要人工校验，因此以 Commit 为单位逐步推进；已 Commit 的内容视为暂定进度/继续推进
- 共享上下文：现有渲染架构文档（`./docs/architecture/client/render/`）作为本次重构的共享上下文，重构过程中的设计、进展和结论应及时写入文档，避免依赖历史对话传递信息
- 任务独立性：每个细分任务完成时，应将当前进展和必要结论 Commit 到文档，后续任务原则上无需阅读旧对话记录（`./docs/deprecated/prompt/`）
- 分支隔离：本次重构仅在专用分支进行，避免影响其他开发

## 重构阶段

1. 渲染基准测试（已完成）：建立性能基线，为后续重构提供对比依据
2. 渲染链路分析：梳理完整渲染链路，定位性能开销，评估理想渲染方案的性能上限，确定重构范围与方案
3. 渲染重构：按方案逐步修改代码、调试并验证性能
4. 跨版本统一：逐步实现 1.20.1-26.3 渲染体系统一

## 分支与版本策略

本次重构仅涉及以下分支：
- 当前版本：`Render-refactor`，作为本次重构的主分支
- 任务分支：在任务完成后会合并到`Render-refactor`的分支
- 26.3 版本：`Render-refactor-26.3`，隔离非渲染相关开发

版本差异处理遵循以下原则：
- 无需关注 1.20.1-26.3 之间的其他版本差异，也无需追溯各项差异的引入版本
- 重点关注 26.2 引入的延迟渲染框架，这是本次重构需要考虑的最大差异
- 26.3 已包含其他版本差异的改动，因此 26.3 验证通过即可视为 1.20.1+ 全版本方案可行；其他版本的差异适配由用户后续处理

基准测试入口：`./docs/architecture/client/render/benchmark/Home.md`（各批次报告与分工）

约定：
- 原始测试数据无需重复阅读，报告已总结关键数据和结论
- 在定位性能开销、正式开始渲染重构时，分别是单独的新的基准测试
- 其他任务无需阅读原始测试数据
- 统一使用`DebugKey`作为调试开关
- 阶段 0 测量已结束（`26.35.11.1-1` / `-2` / `-3` 三批），后续新增探针随重构代码一起加，不再单独跑采集批次

### 当前结论

1. TaCZ：1.2.0 除静态展示渲染优化外，其余渲染性能与 1.1.8 基本一致；由于本次目标是彻底解决渲染性能问题，无需参考其实现（其实现本身不公开、缺文档与缺陷分析，且 `26.35.11.1` 中与加速渲染同装无收益；差异只登记为待验证点，见 [`refactor/reference-tacz-1.2.0.md`](./refactor/reference-tacz-1.2.0.md)，已测数值不改动）
2. Accelerated Rendering：目前无法解释其未能提升渲染性能的原因，且该模组不支持 26.2+（原版延迟渲染框架），因此不参考其实现
3. 性能瓶颈：当前裸 1000+ FPS 测试场景存在 CPU 瓶颈，同时 GPU 利用率未充分发挥，后续需要针对两方面分析
4. 架构调整：需要大幅调整当前已完成跨版本统一的渲染体系，现有跨版本统一封装必然被破坏，不应将其作为重构约束
5. 实施顺序：
    - 优先在 1.20.1 完成重构并测试验证
    - 设计阶段需同步考虑方案与 MC 26.2+ 延迟渲染框架是否存在根本冲突
    - 用户验证通过后再在 26.3 实现并验证跨版本方案
    - 根据 26.3 实现情况，可能调整为由 1.20.1-26.1.2 等低版本适配高版本的渲染模式
6. 满配枪械（`26.35.11.1-3`）把每枪 draw 数抬到 9 次、瞄具模板成为第一人称最大单项，因此 **B2 的跨实例合批是 multi 达标的必要条件**，不再是可选加分项

## 渲染重构方案

入口：`./docs/architecture/client/render/refactor/Home.md`

- 方案只写取舍与路线，成本事实与量级仍以 `./docs/architecture/client/render/chain/` 为准
- 目标：以空手帧时间（0.795–0.80 ms，≈1250–1300 FPS）为优化上限，把单次提交压到「draw + 少量状态切换」的量级
- 结论先行：当前大头是每帧重新生成全部顶点（55.8%）与每次 flush（21.2%）；微优化只能拿到系数收益，必须改变成本模型（烘焙 / 合并 draw）
- 方案分档：A 微优化、B 几何烘焙（B1 模型空间 / B2 静态实例世界空间合并）、C 跨实例 draw 合并、D 剔除与 LOD、E 多线程（暂不实施）
- **路线已定（满配批次之后）**：B1-a 静态烘焙 → B1-b 第一人称 → **B1-c 光照解耦** → B2 跨实例合并。B2 是 multi 达标的必要条件（每枪 9 次 draw，仅 draw 就是 0.72 ms/帧），A 的剩余项并入 B1-a；目标与分阶段预估见 `refactor/Home.md` 的「分阶段预期效果」
- **B1-c 已认定必需**：光照变化不用平均帧时间衡量，而是 `b1-b-3` 实测的 2.6–2.9 次/秒、单次 0.6–9.2 ms 尖峰；它决定 1% low / 0.1% low，观感是持续卡顿。B2 合并后一次光照变化会重建整批，必须在 B2 之前定下「光照与几何分离」的批次布局。
- **B1-c 的拆分已实测**（`b1-b-3` 第 5–8 次）：光影下 9.2 ms 的 94% 是顶点发射（Oculus 扩展格式让 `BufferBuilder` 失去快速路径），上传仅 0.49 ms、新建缓冲 0.05 ms。因此「原地重写 uv2」与「独立 uv2 流」都能消掉尖峰；**先做改动更小、跨版本更保守的原地重写，独立 uv2 流留作后续降低上传/显存的优化**。取舍、CPU/GPU 成本与光影兼容性见 [`refactor/lighting-decoupling.md`](./refactor/lighting-decoupling.md)
- 每个阶段以 Commit 为单位验收，测量口径与新增探针见方案文档的「测量与验收」
