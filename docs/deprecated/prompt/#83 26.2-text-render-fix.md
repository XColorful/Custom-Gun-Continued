## 结论

**都不是。** 这条既不是 #81 的 `bakePipelineState`，也不是 #82 的 `_disableDepthTest`。它属于第三个来源，但和 #81 同属「必须在 submit 窗口内完成」这一类——具体说，和 #36 里修手臂/非瞄具配件时踩的坑一模一样。

## 证据链

1. **不是透明度问题**。[TextRender.java:69](core/src/main/java/dev/xcolorful/customgun/client/renderer/model/TextRender.java:69) 里 `ColorUtils.ARGB32.opaque(...)` 还在（[`_ModelNodeTextDisplay`](core/src/main/java/dev/xcolorful/customgun/client/resource/assets/display/_ModelNodeTextDisplay.java:16) 默认 `textColor = 0xFFFFFF`，alpha 为 0，所以这行仍然必要）。26.2 的 `submitText` → `Font.prepareText` 会原样使用该 alpha，不会再自动补。

2. **文字根本没提交出去。** `TextRender.render` 本身跑在 flush 阶段（它是节点上的功能渲染器，由 [`ModelObject.render:220`](core/src/main/java/dev/xcolorful/customgun/client/model/ModelObject.java:220) 的 `shouldRender` 循环调用，而该循环位于 `submitCustomGeometry` 的回调里），接着它又 `modelObject.delegateRender(...)` 推迟到同一回调末尾；真正取 collector 时，[`TextRender.java:65`](core/src/main/java/dev/xcolorful/customgun/client/renderer/model/TextRender.java:65) 的 `collector == null` 直接 return。

3. **collector 确实已空。** [GunItemRenderer.java:288-293](core/src/main/java/dev/xcolorful/customgun/client/renderer/item/GunItemRenderer.java:288) 是 `set collector → render → finally set null`；而原版在它返回**之后**才 flush：

```java
this.itemInHandRenderer.submitHandsWithItems(..., this.handAndScreenSubmitNodeStorage, ...);
this.featureRenderDispatcher.renderAllFeatures(this.handAndScreenSubmitNodeStorage);
```

（`GameRenderer.renderItemInHand`，26.2 sources 364 行）所以 flush 时 ThreadLocal 必为空。

4. **这是已知坑的漏网之鱼。** [`_GunModelRender._renderHand`](core/src/main/java/dev/xcolorful/customgun/client/model/_GunModelRender.java:192) 的注释就写着「flush 阶段 collector 已被清空」，当初为手脚/配件专门加了 submit 期的路径渲染。文字没跟着改。

## 与两条历史修复的差异

| | 出问题的环节 | 修法 |
|---|---|---|
| #81 激光 | 提交了，但模板状态没在提交期烘焙进 RenderType | `bakePipelineState` |

所以两者的任何一行都不能直接套用：文字没有模板状态可烘焙，也走不到深度测试。

## 修复方向（未动代码）

和 `_renderScope` / `_renderHand` 同一套：给文字节点缓存 path（`ModelObject.getPath` 现成，参照 `scopePosPath`），在 **submit 阶段**沿 path 摆位并 `submitText`，`TextRender` 不再依赖 `delegateRender` 和 ThreadLocal。因为 `GunModelObject` 和 `AttachmentModelObject` 都继承 `ModelObject`，放在 `ModelObject.render` 的 submit 段可以一次覆盖两者；同时要把 `setFunctionalRenderer(name, ...)` 那条挂载去掉，否则 flush 期还会跑一遍。

有一条路不能走：把 collector 延长到 flush 之后再提交。`FeatureRenderDispatcher.prepareFrame` 在 `execute*` 之前已经 `drainPhases` 并切好片，flush 期间再 submit 只会落到下一帧，表现为延迟一帧 + 抖动。

以上结论全部来自静态链路核对，**没有进游戏验证**。
