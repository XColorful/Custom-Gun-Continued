# 测试数据计算报告（CGC 1.20.1 · b1-b-3：光照变化下的重烘焙）

**数据**：本目录 8 次独立启动（n=8），每次含 Afterburner 与 F12 两段，时间不重叠。
- `cgc1 (N).txt`：Afterburner 7 步 = 空手（夜晚静止）/ ak47 移动 / ak47+光影 静止 / ak47+光影 移动 / 满配 移动 / 满配+光影 静止 / 满配+光影 移动
- `cgc1-builtin (N).txt`：F12 4 段 = ak47 移动 / ak47+光影 移动 / 满配 移动 / 满配+光影 移动
- 第 5–8 次采集起，F12 报告新增 `Bake emit` / `Bake buffer create` / `Bake upload` 与计数器 `Bake upload bytes`；第 4 节的烘焙拆分只统计这 4 次（n=4），其余各节为 n=8。

**场景**：夜晚、脚下火把、按 W 走 8 格后由命令方块传送回起点、再走 16 格；移动时每跨一格方块光 −1，约每秒 2.6–2.9 次光照变化。
**口径**：帧时间 = 1000 / FPS；均值 ± 1 样本标准差。`Static bake` 的探针平均值是**命中帧内所有烘焙之和**，不是单次烘焙；命中帧比例 × FPS = 重建帧/秒。单次光照变化字节 = 每帧平均字节 ÷ 命中帧比例。手动起停误差 ≤0.5–1 s。
**复现**：`python analyze.py`。

## 1. 帧时间（Afterburner，n=8）

|步骤|AF 帧时间|1% low|
|---|---:|---:|
|空手（夜晚静止）|0.810 ± 0.021 ms（1234.5 FPS）|512.7|
|ak47 移动|1.199 ± 0.031（833.9）|337.9|
|ak47+光影 静止|6.528 ± 0.043（153.2）|138.2|
|ak47+光影 移动|6.353 ± 0.022（157.4）|136.7|
|满配 移动|1.416 ± 0.028（706.3）|331.6|
|满配+光影 静止|7.057 ± 0.030（141.7）|115.7|
|满配+光影 移动|**6.898 ± 0.030**（145.0）|**59.1**|

- 无光影没有静止对照，移动段的 AF 增量（0.389 / 0.606 ms）混有走动本身（世界侧）的成本，**枪械成本以第 2 节的 CGC 探针为准**。
- 光影下移动比静止还快 0.16–0.18 ms，方向与预期相反，见第 6 节；两者的 10 s 记录在同一进程内。
- **只有「满配 + 光影」的 1% low 明显下降**（115.7 → 59.1）；ak47+光影移动（136.7）与静止（138.2）几乎一致。这与实机观察一致：只有满配+光影能看到明显周期性 low 帧，ak47 偶尔有小幅波动。原因见第 3 节：尖峰只在重建成本超过该帧的 CPU 余量时才变成掉帧。

## 2. 重建的次数与成本（F12，移动段，n=8）

|项|ak47 移动|ak47+光影|满配 移动|满配+光影|
|---|---:|---:|---:|---:|
|CGC|0.200 ± 0.005|0.353 ± 0.021|0.475 ± 0.009|1.470 ± 0.133|
|`Bake rebuilds`（次/帧）|0.020|0.130|0.060|0.340|
|重建帧比例|0.30%|1.80%|0.40%|2.00%|
|重建次数/秒|**2.6**|**2.8**|**2.8**|**2.9**|
|单次重建（该帧合计）|**0.603 ± 0.014 ms**|**2.700 ± 0.183 ms**|**1.372 ± 0.031 ms**|**9.246 ± 0.848 ms**|
|每次重建的块数|≈6.7|≈7.2|≈15|≈17|
|p99 帧时间|2.292 ms|9.662 ms|2.549 ms|**15.438 ms**|
|最大帧时间|11.736 ms|13.852 ms|7.655 ms|**27.626 ms**|

- **重建次数只跟走路有关**：约 2.6–2.9 次/秒，三种配置一致；光影下比例变大（1.8%–2.0%）只是因为帧率低（157 / 145 FPS），次数没变。
- 一次光照变化会重烘整枪的块：ak47 约 7 块、满配约 15–17 块（含瞄具模板的网格）。之后连续走后光强降到 0 就不再变化。
- 光影下单次重建贵 4.4–6.7 倍（2.700 / 9.246 ms）。**第 4 节的拆分证明这不是上传/驱动停顿，而是顶点发射本身。**

## 3. 对帧时间的影响

|场景|命中帧占比|单次|折合每帧平均|
|---|---:|---:|---:|
|ak47|0.30%|0.603 ms|1.8 µs（0.16%）|
|ak47+光影|1.80%|2.700 ms|49 µs（0.76%）|
|满配|0.40%|1.372 ms|5.5 µs（0.39%）|
|满配+光影|2.00%|9.246 ms|**185 µs（2.7%）**|

- **平均帧时间几乎不受影响**：移动段的 CGC 0.200 / 0.475 与静止（`26.35.11.1-5` 的 0.202 / 0.540）持平；光照重建只占 0.4%–2.7%。
- **尖峰按命中率决定落在哪个分位**：无光影命中率 0.3%–0.4%，低于 1% 分位，所以只体现在 0.1% low；光影下命中率 1.8%–2.0%，高于 1% 分位，1% low 直接被重建帧决定（满配 115.7 → 59.1，p99 帧时间 9.3 → 15.4 ms，最大 27.6 ms）。
- **为什么只有满配+光影肉眼可见**：ak47+光影的单次重建 2.70 ms 小于该帧 6.35 ms 的总时长，光照帧仍落在正常帧内（1% low 136.7 vs 静止 138.2，噪声内）；满配+光影的 9.25 ms 超过 6.90 ms 的帧，p99 帧时间被抬到 15.4 ms（多出约 8.5 ms），才形成 1% low 59.1。**判据是「重建成本是否超过该帧的 CPU 余量」**，不是绝对成本。
- 无光影的 1% low（337.9 / 331.6）比 `b1-b-1` 的静止（464 / 415）低，但本批没有无光影静止对照，不能全部归因于光照重建（走动本身也有成本，见第 1 节）。

## 4. 烘焙成本拆分（第 5–8 次，n=4）

|项|ak47 移动|ak47+光影|满配 移动|满配+光影|
|---|---:|---:|---:|---:|
|`Static bake`（命中帧合计）|0.611 ± 0.013|2.665 ± 0.149|1.361 ± 0.040|9.395 ± 0.970|
|`Bake emit`（顶点发射）|**0.474 ± 0.009**|**2.502 ± 0.144**|**1.111 ± 0.033**|**8.844 ± 0.916**|
|`Bake buffer create`|0.013 ± 0.001|0.014 ± 0.001|0.023 ± 0.001|0.049 ± 0.004|
|`Bake upload`|0.117 ± 0.008|0.146 ± 0.005|0.223 ± 0.008|0.494 ± 0.057|
|emit 占比|77.6% ± 1.0|93.9% ± 0.2|81.6% ± 0.3|94.1% ± 0.3|
|单块重建字节|57.9 KB|76.8 KB|60.3 KB|102.0 KB|
|单次光照变化字节|385.8 KB|554.9 KB|904.1 KB|1733.8 KB|

- **顶点发射是绝对大头（78%–94%）**；新建 `VertexBuffer` 只占 0.5%–2.2%，上传只占 5.3%–19.4%。
- 「单块重建字节」= 每帧平均字节 ÷ 每帧 `Bake rebuilds`；「单次光照变化字节」= 每帧平均字节 ÷ 命中帧比例，即一次光照变化整枪的总字节。
- **光影下 emit 贵在 BufferBuilder 失去快速路径**：`BufferBuilder.switchFormat` 只对 `DefaultVertexFormat.NEW_ENTITY` 精确匹配时启用 `fastFormat`；Oculus 的 `MixinBufferBuilder` 在 `begin` 之前把格式换成 `IrisVertexFormats.ENTITY`（52 B，多出 entityId / midTexCoord / tangent），于是每个顶点都走通用逐元素路径，并额外写三个属性。upload 仍然便宜（满配 1.73 MB / 0.494 ms）。
- **前一批的推测被否定**：9 ms 不是「上传时 GPU 队列已满／新建缓冲停顿」，而是纯 CPU 顶点生成。复用 `VertexBuffer` 最多省 0.05 ms，解决不了问题；只有「不重新发射顶点」才能消掉尖峰。
- **两条光照解耦路线都能消掉 emit**：A 只写 4 B/顶点光照流（满配约 133 KB，按实测上传线性折算约 0.04 ms），B 保留 CPU 副本后 patch + 全量重传（约 1.73 MB / 0.49 ms）。两者都远低于普通帧时长；A 相对 B 每次再省约 0.45 ms，折合平均约 0.13%（2 次/秒时），**不是消除掉帧的必要条件**。

## 5. 结论（对应 V2）

1. **光照变化不会让优化全没**：平均 CGC 不变；只有跨过亮度边界的那一帧退回重构前的单帧成本，每秒 2.6–2.9 次、占比 0.3%–2.7%。
2. **观感**：夜间连续走动会有周期性卡顿——无光影落在 0.1% low，满配+光影落在 1% low（约 17–28 ms 的帧）。ak47+光影的 2.7 ms 能塞进 6.35 ms 的帧，所以肉眼几乎看不到；满配+光影的 9.2 ms 塞不进，才有明显 low 帧。
3. **光照解耦是必要优化**（2026-11-13 决策）：尖峰决定 1% low，且 B2 合并后一次光照变化会重建整批。实测拆分进一步确认：**尖峰来自顶点发射，A/B 两条路线都能消除它**。
4. **两条路线的取舍已被数据改写**：B（CPU 副本 + 交错缓冲原地重写）的剩余成本约 0.49 ms 上传 + 43 µs patch，已经足够把掉帧消掉，且不改顶点格式/attribute、跨版本最保守；A（独立 uv2 流）每次再省约 0.45 ms，但需要覆盖 attribute slot 4，26.3 的第二 binding 仍未验证。**建议先实现 B，把 A 作为后续降低上传/显存与缓存键的优化**，而不是把 A 当作消除掉帧的前置条件。
5. **不要只改重建路径**：复用 `VertexBuffer`、提高每块网格的光照条目上限都只影响 0.5%–2.2% 的 `Bake buffer create` 与缓存命中，不能解决 emit 的 78%–94%。

## 6. 说明与异常

- 光影下「移动」比「静止」快 0.16–0.18 ms（满配 7.057 → 6.898）：两次记录在同一进程内，最可能是一次性预热 / 视角差异，无法从本批数据分离。它不影响第 2 节的结论——重建次数与单次成本由 F12 直接测得。
- 静止记录的采样点就是火把位置：火把有火焰/烟粒子，光影包在光源附近也可能更贵，这可以解释静止反而更慢。若要做这个对照，把火把换成 `minecraft:light` 方块（不可见、无粒子，`/setblock ~ ~ ~ light[level=15]`）或萤石再测一次即可。
- 「静止」记录在火把位置（方块光 14），「移动」离开火把、光照逐格下降，到 14 格外为 0；因此一半的路程之后不再触发重建，2.6–2.9 次/秒比「每格一次」低。
- 命令方块传送回起点会让光照瞬间从 0 跳回 14，也触发一次重建；每段约 1 次。
- 第 1–4 次采集没有烘焙拆分探针，所以第 4 节 n=4；第 4 节的 `Static bake` 也只在这 4 次上取均值，与第 2 节的 n=8 均值有约 0.1 ms 的批次差。
- 手动起停（左手 W + 右手 F12/Afterburner 热键）误差 ≤0.5–1 s，只影响 AF 的平均值，不影响 F12 的计数类指标。
- 光影下 `CGC GPU busy` 不可信，本批未用于归因。
