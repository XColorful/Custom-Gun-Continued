# 渲染链路：CPU / GPU 利用与优化上限

> 本文回答两个问题：当前帧时间由 CPU 还是 GPU 决定，以及「空手帧时间」为什么可以作为重构的优化上限。它是 [渲染链路分析](./Home.md) 的最后一块事实，结论供 [渲染重构方案](../refactor/Home.md) 使用；本文仍只陈述事实与量级，不给方案。
>
> 数据来源：[基准测试报告](../benchmark/26.35.11.1-1/测试数据计算报告.md)（内置探针，1.20.1 与 26.3 各 6 次重复）与 [端间对比报告](../benchmark/26.35.11.1/测试数据计算报告.md)。除引用值外，本文数字一律标「推算」或「待测」。

## 结论

1. **当前是 CPU 瓶颈**，具体是「渲染线程单线程上的顶点生成 + 提交」，不是 GPU 填充率或带宽。
2. **GPU 余量没有实测数据**，但从几何量、显存带宽和 draw 数量级推算，枪械不是 GPU 侧的负担；真正的疑点是每次 `endBatch` 里缓冲上传与 draw / 状态切换各占多少，以及近景 overdraw。
3. **优化上限 = 空手帧时间**：0.795–0.800 ms/帧（1257.8 / 1250.2 FPS）。标准场景与第一人称的可压缩空间是 CGC 的 0.5565 ms/次；multi 还要额外扣除场景自身的 1.2–1.33 ms 基线（见「优化上限的推导」）。
4. CPU 的「未充分利用」不是核心利用不足，而是**单核串行**：渲染线程占满一个核，其余核心在渲染阶段无事可做，而顶点生成目前无法被自动并行。

## 判定 CPU 瓶颈的证据

|证据|数据|推论|
|---|---|---|
|增量随提交次数线性，与像素覆盖无关|第一人称单枪 +0.6725 ms（CGC 0.5565），展示框单枪 0.5261 ms；multi 9 把 ≈ 4.73 ms|时间跟着「提交次数 × 几何量」走，不是屏幕面积|
|同一份 CPU 代码在延迟渲染下变快|1.20.1 几何+提交 0.4288 ms，26.3 flush 回调 0.2303 ms（54%）；持枪增量 −17%，multi 帧时间 −39%|CPU 顶点生成减少 → 帧时间同步下降|
|清空 / 空手立即回到基线|`/clear` 0.7924 ms、空快捷栏 0.8003 ms；不提交即无成本|不存在后台 GPU 常驻开销|
|1% low 明显低于均值|empty 494.7 / 持枪 345.1 FPS|存在帧间抖动，来源待测（分配 / GC / 驱动提交）|

如果瓶颈在 GPU，减少 CPU 顶点生成不会带来帧时间下降；26.3 的对照否定了这一点。

## GPU 侧的量级推算

以多场景 9 把枪、每把 445 立方体、每顶点 36 字节（`DefaultVertexFormat.NEW_ENTITY`：position 12 + color 4 + uv 8 + overlay 4 + light 4 + normal 3，对齐后 36）估算：

|量|单把|9 把|对照|
|---|---:|---:|---|
|立方体/帧|445|4005|探针计数（实测）|
|顶点/帧|10 680|96 120|×24（实测×推算）|
|顶点数据/帧|≈384 KB|≈3.5 MB|推算|
|165 FPS 下带宽|—|≈0.57 GB/s|GTX 1660 SUPER 约 336 GB/s，占 0.17%|
|draw 估算|1（枪体）+ 每个实际渲染的配件 + 瞄具部件|9–63|推算；基准里的枪未触发配件 delegate，实测每枪 1 次|

结论：**顶点吞吐与显存带宽都不可能成为瓶颈**。GPU 侧真正需要确认的只有两项：draw call / 状态切换的驱动开销，以及枪体近景的 overdraw（填充率）。两者都缺少实测。

## draw 成本：从 `endBatch` 反推

内置探针的计数器给出了第一人称的真实 flush 次数（`benchmark/26.35.11.1-1/*-builtin*.txt`）：

|场景|提交|`endBatch calls`|`Geometry batches`（`getBuffer`）|`endBatch flush`|
|---|---:|---:|---:|---:|
|第一人称|1|3.00|4|0.1180 ms|
|multi（9 展示框）|9|9.00|9|0.9090 ms|
|第一人称 + 9 展示框|10|12.00|13|0.9730 ms|

- 第一人称的 3 次 = 枪体 1 次（`ModelObject.render`）+ 左右手各 1 次（`HandRender`）；文字节点、枪口火焰与激光不自行 flush，由下一次 flush 带走。
- 单次 `endBatch` ≈ **40 µs**（0.1180 / 3）。
- multi 的 9 次 ≈ **101 µs/次**，明显高于第一人称：这些 flush 冲的是**同帧共享的全局缓冲源**，里面还排着 9 个展示框实体本身的几何。

上传字节与耗时高度吻合：一把枪约 384 KB 顶点数据，按 10 GB/s 的内存 / 总线带宽约 38 µs，与 40 µs/次同量级（推算）。因此 **`endBatch` 的主体很可能是缓冲上传，而不是 draw 本身**；持久 VBO 的收益主要来自去掉每帧上传。

这同时给出一条新的下限：顶点生成归零后，成本 = `draw 数 × 单次 draw` + `新增上传字节`。单次 draw（不含上传）的量级尚未测得，是重构前必须补的测量项。

> 待测：现有 `endBatch flush` 探针无法区分「缓冲上传」与「draw / 状态切换」。两者在新方案里命运不同——持久 VBO 可以去掉上传，但去不掉 draw——因此必须拆开测量。

## 单核与多核

- 渲染线程只有一条（1.20.1 的 `GameRenderer.renderLevel` → 实体循环 → 手部 → GUI 串行），顶点生成全部发生在这条线程上。
- 测试机为 i5-9400F（6 核 6 线程）；持枪 / multi 时渲染线程接近占满，其余核心在渲染阶段基本空闲。
- 「CPU 未充分利用」应理解为**没有把顶点生成分摊到多核**，而不是主线程还有空档：`/clear` 与空手的高帧率说明主线程在无枪时并不慢。
- 多线程能否变现取决于数据依赖：每把枪的几何生成彼此独立（共享的只有资源实例与缓冲源），理论上可并行；但当前 `BufferBuilder` / `BufferSource` 不是线程安全的，且渲染线程必须等待结果，收益受最慢分片与同步开销限制。**待测**。

## 优化上限的推导

上限取「空手帧时间」，即画面里有枪但不渲染枪时的整帧时间：

|口径|值|
|---|---:|
|空快捷栏（批次 26.35.11.1）|0.795 ms（1257.8 FPS）|
|空快捷栏（批次 26.35.11.1-1）|0.8003 ms（1250.2 FPS）|
|用户给出的上限口径|≈1300 FPS ≈ 0.77 ms|

这个上限只对**标准场景**成立。multi（9 个展示框 + 9 个石头方块 + HUD）里即使 CGC 成本为 0，帧时间也不是 0.80 ms：

- 实测 multi 帧时间 6.0688 ms、CGC 4.7348 ms，差值 **1.334 ms** 是「场景本身 + CGC 探针未覆盖的部分」；
- 同场景 TaCZ 1.2.0 的整帧是 1.185 ms（含 9 把枪），说明场景基线不高于 1.185 ms；
- 两者共同给出 multi 的可逼近下限约 **1.2–1.33 ms**（推算）。

因此 multi 的目标不是接近 0.80 ms，而是接近场景基线；CGC 在 multi 里的可压缩空间约 4.7 ms 中的绝大部分，但终点比标准场景高 0.4–0.5 ms。

「优化上限」不是「帧时间等于空手」——只要还要画枪，就至少要付 draw 与少量状态切换。可压缩空间的定义是：

```
可压缩空间 = 当前帧时间 − 场景基线（空手 / 无枪场景）
当前 CGC 成本：multi 4.7348 ms / 第一人称 0.5565 ms / 展示框单枪 0.5261 ms
```

|场景|当前帧时间|当前 CGC|场景基线|CGC 可压缩|
|---|---:|---:|---:|---:|
|multi 9 展示框|6.0688 ms|4.7348 ms|1.2–1.33 ms|≈4.7 ms|
|第一人称持枪|1.4727 ms|0.5565 ms|0.795 ms|0.68 ms（其中约 0.12 ms 是入口 / 相机 / 状态等非 CGC 探针项）|
|展示框单枪|≈0.526 ms|≈0.526 ms|0|0.526 ms|

上限的判定标准因此分成两层：

1. **单次提交成本**：从 0.526 ms 压到「一次 draw 的量级」（10⁻² ms），对应顶点生成归零。
2. **提交次数**：multi 下 9 次提交如果各自仍要若干次 draw，就需要把 draw 合并或复用；否则单次成本再低，也会被次数放大。

## 测量缺口

现有探针覆盖 CPU 侧阶段，缺 GPU 与驱动侧数据。要判定「是否还有 GPU 余量」以及「新方案的 draw 下限」，至少需要：

|指标|现状|用途|
|---|---|---|
|GPU 忙时 / GPU 利用率|无（原版 F3 有，但未记录）|判定 CPU-bound 是否成立、优化后是否会转为 GPU-bound|
|每次 draw 的耗时|只有 `endBatch` 合计|拆分上传与 draw，确定持久 VBO 的收益|
|上传字节数 / 帧|无（可由 `Cubes submitted × 24 × 36` 估算）|确认带宽结论、发现重复上传|
|draw call 数 / 帧|`endBatch calls` 计数器|合并 draw 的收益基线|
|帧内分配字节数|无|解释 1% low 抖动、评估 GC 影响|
|overdraw / 填充率|无|第一人称近景的 GPU 成本边界|

### 可行的采集方式

- **整帧 GPU busy**：1.20.1 原版已自带 `com.mojang.blaze3d.systems.TimerQuery`（F3 的 GPU 使用率图用它），实现是 `GL_ARB_timer_query` + 延迟读取。可直接复用，或按同样的方式在 `PREPARE_RENDER_FRAME_EVENT` / `RENDER_FRAME_EVENT` 之间计时。
- **注意**：同一次查询不能嵌套；必须延迟一帧读取并先查 `GL_QUERY_RESULT_AVAILABLE`，否则会阻塞并污染 CPU 探针；NVIDIA 上实际量化约 0.5–1 µs，单次几十微秒的区间误差大，应跨帧累加。
- **拆分 `endBatch`**：在 `BufferUploader._drawWithShader` 前后分别计时（需要 mixin），或直接在 CGC 侧用「顶点字节 ÷ 带宽」与「draw 数 × 估算」交叉验证。
- **光影下**：Oculus 会把 `endBatch` 变成入队，真正的上传 / 绘制由它稍后执行；此时包在 CGC `endBatch` 外的 GPU 查询接近 0，**只有整帧查询可信**。
- **26.3**：提交与绘制分离，对 CGC 提交区间做 GPU 查询没有意义；需要统计提交次数、提交字节、flush 后的 draw 命令数与 render pass 数，整帧查询仍然通用。

判定阈值（推算，待首批日志校准）：`GPU busy / 帧时间 < 0.7` 判 CPU-bound；`0.7–0.9` 为混合；`> 0.9` 判 GPU-bound。帧预算按 165 Hz 的 6.06 ms 计。

采集开关沿用 `DebugKey`（F12）与 `customgun-render-profile.txt`，新增指标并入现有格式。具体插入点与验收口径见 [重构方案：测量与验收](../refactor/Home.md#测量与验收)。
