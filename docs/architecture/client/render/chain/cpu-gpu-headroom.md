# 渲染链路：CPU / GPU 利用与优化上限

> 本文回答两个问题：当前帧时间由 CPU 还是 GPU 决定，以及「空手帧时间」为什么可以作为重构的优化上限。它是 [渲染链路分析](./Home.md) 的最后一块事实，结论供 [渲染重构方案](../refactor/Home.md) 使用；本文仍只陈述事实与量级，不给方案。
>
> 数据来源：[基准测试报告](../benchmark/26.35.11.1-1/测试数据计算报告.md)（内置探针，1.20.1 与 26.3 各 6 次重复）与 [端间对比报告](../benchmark/26.35.11.1/测试数据计算报告.md)。除引用值外，本文数字一律标「推算」或「待测」。

## 结论

1. **当前是 CPU 瓶颈**，具体是「渲染线程单线程上的顶点生成 + 提交」，不是 GPU 填充率或带宽。几何遍历占 CGC 的 57%（标准持枪）到 77%（multi）。
2. **GPU 余量仍无有效数据**。第二批测到了 draw 与上传的单位成本（约 10 µs/draw、5–6.5 GB/s），但整帧 GPU 查询测的是命令跨度、不是利用率（见下）。
3. **优化上限 = 空手帧时间**：无探针构建约 0.795–0.800 ms/帧（≈1250–1300 FPS），本批含探针约 0.862 ms。标准场景与第一人称的可压缩空间是 CGC 的 0.507 ms/次；multi 的场景基线实测为 0.852 ms，可压缩空间约 4.6 ms（帧时间差）。
4. CPU 的「未充分利用」不是核心利用不足，而是**单核串行**：渲染线程占满一个核，其余核心在渲染阶段无事可做，而顶点生成目前无法被自动并行。

## 判定 CPU 瓶颈的证据

|证据|数据|推论|
|---|---|---|
|增量随提交次数线性，与像素覆盖无关|第一人称单枪 +0.583 ms（CGC 0.507），展示框每把帧时间 0.511 ms（CGC 0.461）；multi 9 把 CGC 4.146 ms|时间跟着「提交次数 × 几何量」走，不是屏幕面积|
|同一份 CPU 代码在延迟渲染下变快|1.20.1 遍历+flush 0.395 ms，26.3 flush 回调 0.233 ms（59%）；multi 帧时间 5.449 → 3.851 ms|CPU 顶点生成减少 → 帧时间同步下降|
|清空 / 空手立即回到基线|`/clear` 0.856 ms、空快捷栏 0.862 ms；不提交即无成本|不存在后台 GPU 常驻开销|
|1% low 明显低于均值|空手 484.1 / 持枪 353.6 FPS|存在帧间抖动；每枪分配仅约 0.10 MB，不是主因|

如果瓶颈在 GPU，减少 CPU 顶点生成不会带来帧时间下降；26.3 的对照否定了这一点。

## GPU 侧的量级推算

以多场景 9 把枪、每把 445 立方体、每顶点 36 字节（`DefaultVertexFormat.NEW_ENTITY`：position 12 + color 4 + uv 8 + overlay 4 + light 4 + normal 3，对齐后 36）估算：

|量|单把|9 把|对照|
|---|---:|---:|---|
|立方体/帧|445|4005|探针计数（实测）|
|顶点/帧|10 680|96 120|×24（实测×推算）|
|顶点数据/帧|≈384 KB|≈3.5 MB|推算|
|165 FPS 下带宽|—|≈0.57 GB/s|GTX 1660 SUPER 约 336 GB/s，占 0.17%|
|draw 估算|1（枪体）+ 每个实际渲染的配件 + 瞄具部件|9–63|推算；基准里的枪未触发配件 delegate，实测每枪 1 次|

结论：**顶点吞吐与显存带宽都不可能成为瓶颈**。第二批加上了整帧 GPU 查询，但它实测恒为帧时间的 99.4%–99.8%（空手 0.835/0.840、持枪 1.428/1.435、multi 5.178/5.187）。`GL_TIME_ELAPSED` 跨越两次帧事件，测的是 GPU 命令跨度，CPU 间断提交时这个跨度自然等于帧时间；**它既可能在 GPU 饱和时出现，也可能在 GPU 大量空等时出现，不能用来判定余量**。要回答还需要把查询缩小到 CGC 自己的 draw 区间、使用驱动计数器，或做「逐步减少工作量」的扫描。

## 上传与 draw：实测拆分

第二批把整帧所有 `BufferUploader` 调用按上传与 draw 分开计时；CGC 归因值 = 同端「有枪」−「无枪」：

|场景|CGC 上传|CGC draw|CGC draw 数|单次 draw|上传带宽|
|---|---:|---:|---:|---:|---:|
|第一人称持枪|0.077 ms|0.037 ms|4|**9.3 µs**|4.9 GB/s|
|multi 9 展示框|0.535 ms|0.181 ms|约 18|**10.1 µs**|6.5 GB/s|
|multi + 手持枪|0.648 ms|0.239 ms|约 24|9.8 µs|—|

- 上传与 draw 合计 0.716 ms，占 multi 显式 flush 0.794 ms 的 90%。**上传约占 flush 的 2/3，draw 约占 1/4。**
- 上传带宽 5–6.5 GB/s，与「384 KB/枪」的数据量吻合。
- 单次 draw 稳定在约 10 µs，在标准与 multi 两个场景一致。

这给出烘焙后的下限：顶点生成归零后，成本 ≈ `draw 数 × 10 µs + 新增上传字节`。持久 VBO 能去掉上传，但去不掉 draw；因此「减少 draw 数」与「去掉上传」是两条独立的收益来源。9 把枪 18 次 draw 若合并到 3–4 次，draw 成本从 0.181 ms 降到 0.03–0.04 ms。

> 口径：`endBatch upload` / `endBatch draw` 是整帧统计，包含世界实体与渲染类型切换触发的隐式 flush；`endBatch flush` 只包 CGC 的显式 `endBatch` 调用，两者不可相加。`Draw calls` 同理，空手帧的 8 次是世界绘制。

## 单核与多核

- 渲染线程只有一条（1.20.1 的 `GameRenderer.renderLevel` → 实体循环 → 手部 → GUI 串行），顶点生成全部发生在这条线程上。
- 测试机为 i5-9400F（6 核 6 线程）；持枪 / multi 时渲染线程接近占满，其余核心在渲染阶段基本空闲。
- 「CPU 未充分利用」应理解为**没有把顶点生成分摊到多核**，而不是主线程还有空档：`/clear` 与空手的高帧率说明主线程在无枪时并不慢。
- 多线程能否变现取决于数据依赖：每把枪的几何生成彼此独立（共享的只有资源实例与缓冲源），理论上可并行；但当前 `BufferBuilder` / `BufferSource` 不是线程安全的，且渲染线程必须等待结果，收益受最慢分片与同步开销限制。**待测**。

## 优化上限的推导

上限取「空手帧时间」，即画面里有枪但不渲染枪时的整帧时间：

|口径|值|
|---|---:|
|空快捷栏（批次 26.35.11.1）|0.795 ms（1257.8 FPS）|
|空快捷栏（批次 26.35.11.1-1）|0.8003 ms（1250.2 FPS）|
|用户给出的上限口径|≈1300 FPS ≈ 0.77 ms|

multi 的场景基线已经单独测过（[`benchmark/26.35.11.1-2/multi-baseline`](../benchmark/26.35.11.1-2/multi-baseline/标准.txt)：9 个石头 + 9 个空展示框、无手持枪）：

|端|FPS（6 次均值 ± 标准差）|帧时间|
|---|---:|---:|
|1.20.1|1174.3 ± 23.9|**0.852 ms**|
|26.3|901.7 ± 42.8|**1.109 ms**|

也就是说 multi 场景本身只比空快捷栏（无探针构建 0.800 ms）多约 0.05 ms，画枪的约 4.6 ms 几乎全是 CGC。上一批由 `6.0688 − 4.7348` 推出的 1.334 ms 并不是场景基线：其中约 0.48 ms 是探针没有覆盖到的 CGC 工作（例如共享缓冲源里被连带 flush 的几何）；本批新增的上传 / draw 计数也证实 flush 的归属分散在多个调用点。

因此 multi 的可逼近下限就是 ~0.85 ms（1.20.1），与标准场景的上限基本一致；CGC 在 multi 里的可压缩空间约 **4.6 ms**（帧时间差），探针直接归因到 4.15 ms。

「优化上限」不是「帧时间等于空手」——只要还要画枪，就至少要付 draw 与少量状态切换。可压缩空间的定义是：

```
可压缩空间 = 当前帧时间 − 场景基线（空手 / 无枪场景）
当前 CGC 成本：multi 4.146 ms / 第一人称 0.507 ms / 展示框单枪 0.511 ms
```

|场景|当前帧时间|当前 CGC|场景基线|CGC 可压缩|
|---|---:|---:|---:|---:|
|multi 9 展示框|5.449 ms|4.146 ms|0.852 ms|≈4.6 ms（探针归因 4.15）|
|第一人称持枪|1.445 ms|0.507 ms|0.795 ms（无探针）|0.65 ms（其中约 0.08 ms 是非 CGC 探针项）|
|展示框单枪|≈0.511 ms|≈0.461 ms|0|0.461 ms|

上限的判定标准因此分成两层：

1. **单次提交成本**：从 0.46–0.51 ms 压到「一次 draw 的量级」（10⁻² ms），对应顶点生成归零。
2. **提交次数**：multi 下 9 次提交如果各自仍要若干次 draw，就需要把 draw 合并或复用；否则单次成本再低，也会被次数放大。

## 测量缺口

现有探针覆盖 CPU 侧阶段，缺 GPU 与驱动侧数据。要判定「是否还有 GPU 余量」以及「新方案的 draw 下限」，至少需要：

|指标|现状|用途|
|---|---|---|
|GPU 忙时 / GPU 利用率|整帧 span 已测（恒为帧时间 99.4%–99.8%）|**不能判定余量**；需要 per-pass 或驱动计数器|
|每次 draw 的耗时|**已测：约 10 µs**（标准 9.3、multi 10.1）|确定持久 VBO 与合并 draw 的收益|
|上传字节数 / 帧|**已测：388 KB/枪，3.49 MB/9 把**|确认带宽结论、发现重复上传|
|draw call 数 / 帧|**已测：标准 12（CGC 4），multi 26（CGC 约 18）**|合并 draw 的收益基线|
|帧内分配字节数|**已测：0.18 MB 标准、0.10 MB/枪**|解释 1% low 抖动、评估 GC 影响|
|overdraw / 填充率|无|第一人称近景的 GPU 成本边界|

### 可行的采集方式

- **整帧 GPU busy**：1.20.1 原版已自带 `com.mojang.blaze3d.systems.TimerQuery`（F3 的 GPU 使用率图用它），实现是 `GL_ARB_timer_query` + 延迟读取。第二批已按同样方式实现，但实测结果只能得到命令跨度（第 5 节）。
- **注意**：同一次查询不能嵌套；必须延迟一帧读取并先查 `GL_QUERY_RESULT_AVAILABLE`，否则会阻塞并污染 CPU 探针；NVIDIA 上实际量化约 0.5–1 µs，单次几十微秒的区间误差大，应跨帧累加。
- **拆分 `endBatch`**：第二批已用 `BufferUploaderMixin` 在 `VertexBuffer.upload` 与 `drawWithShader` 前后分别计时。
- **光影下**：Oculus 会把 `endBatch` 变成入队，真正的上传 / 绘制由它稍后执行；此时包在 CGC `endBatch` 外的 GPU 查询接近 0，**只有整帧查询可信**。
- **26.3**：提交与绘制分离，对 CGC 提交区间做 GPU 查询没有意义；需要统计提交次数、提交字节、flush 后的 draw 命令数与 render pass 数，整帧查询仍然通用。

**整帧查询不能用于 CPU/GPU 判定**：它测的是第一条到最后一条 GPU 命令的跨度，CPU 间断提交时自然等于帧时间。要判定余量，应把查询缩小到 CGC 的 draw 区间、使用驱动的 GPU busy 计数器，或做「逐步减少 CGC 工作量」的扫描。

### 探针自身的开销

第二批新增探针带来约 **0.06–0.09 ms/帧** 的固定开销（26.3 全步骤、1.20.1 除持枪外；空手约 7%、multi 约 1.3%）。26.3 没有 upload/draw mixin 也一样慢，说明开销来自两端共用的整帧 GPU 查询（每帧查询创建 + 可用性轮询）与分配采样。下一步应改为每 N 帧采样一次，或用 fence 代替轮询。

采集开关沿用 `DebugKey`（F12）与 `customgun-render-profile.txt`，新增指标并入现有格式。上述项已在代码中实现：

- `ClientRenderProfiler`：`endBatch upload` / `endBatch draw` 探针，`Draw calls` / `Upload bytes` / `Allocated bytes` / `Animation channels` 计数器，以及 `GPU frame busy` 统计；
- `GpuFrameTimer`：1.20.1 用 `GL_TIME_ELAPSED`，26.3 用 `GpuQueryPool` 时间戳，均延迟读取；
- `BufferUploaderMixin`：1.20.1 中把 `endBatch` 拆成上传与 draw 两段。

采集口径见 [`benchmark/26.35.11.1-2/标准.txt`](../benchmark/26.35.11.1-2/标准.txt)：标准 4 步 + multi 2 段。multi 场景基线（9 个石头 + 9 个空展示框）已在同目录的 [`multi-baseline/`](../benchmark/26.35.11.1-2/multi-baseline/) 测好：1.20.1 1174.3 ± 23.9 FPS（0.852 ms）、26.3 901.7 ± 42.8 FPS（1.109 ms），结果并入该批次报告。具体验收口径见 [重构方案：测量与验收](../refactor/Home.md#测量与验收)。
