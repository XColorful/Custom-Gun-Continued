# 外部参照：TaCZ 1.2.0 相对 1.1.8 的渲染差异

> **定位**：本文只登记「差异」与「待验证点」。它不是 CGC 的实现方案，任何一条都不构成采纳决定；路线仍以 [重构方案](./Home.md) 的 B1 → B2 为准。
>
> 用途：让后续每个阶段在动手前能看到「另一份实现做过什么、结果如何」，再由 benchmark 与光影场景实测判定它在本项目是否成立。验证结论回填到 [`chain/`](../chain/Home.md)（事实）与本文（结论），方案改动仍走 `Home.md` 的验收流程。

## 为什么只能当参照，不能当依据

|事实|后果|
|---|---|
|公开 Issue 791（TaCZ 1.2.0 + ParticleStorm 启动崩溃）中，维护者承认 SBM 的粒子部分「参考了一部分 ParticleStorm，结果用了同一个文件夹」|该库至少有一处代码出处与资源隔离缺少审计，不能假设其实现正确或完整。**该承认只覆盖粒子系统，不能反推网格 / VBO 部分**；但足以否决「照抄即安全」|
|TaCZ 实际开发仓库不公开：多个提交引用的 Issue 号与开源仓库对不上|没有对应的设计文档、重构记录与缺陷分析；公开版只是结果快照，失败路径与回退条件不可见|
|公开版与加速渲染同装时没有帧数提升（`26.35.11.1`：`tacz1 → tacz2` 各步骤均为负收益）|参照实现的收益边界不明，周围存在未知变量；**不改动已测数值**，只作为「其数字不能当目标」的理由|
|SBM 2.6.2 只有编译产物（2.2.2 中没有任何 `v2` 类）|机制只能从类结构 / 字节码推断，本文标注「推断」的条目没有源码级确认|

## 观察到的差异（机制级）

同平台对照基线：`26.35.11.1`，Forge 1.20.1，TaCZ 1.2.0 与 1.1.8 均为静态展示改动前后。

|#|机制|1.1.8|1.2.0 观察到的做法|CGC 现状|与方案的重合度|
|---|---|---|---|---|---|
|1|模型运行时|可变场景图（v1）|烘焙模型 + 逐索引骨骼实例（v2），运行期不做名字查找|可变场景图|B1 的前提相同|
|2|静态几何捕获|无|整枪 + 全部配件 + 变体 / 转接口 + LOD 一次捕获，按 `RenderType` 分桶|每帧逐节点重建|B1|
|3|静态网格缓存|无|持久 VBO，键 =（外观, `ItemDisplayContext`）；容量 128 条 / 256 MB（推断：常量取自字节码）、空闲回收 300 s（TaCZ 代码显式传入）|无|B1|
|4|世界空间合批|无|按 section + `RenderType` 合批，`RenderLevelStageEvent` 每帧统一绘制，按材质顺序 + 距离排序|无|B2|
|5|光照位置|顶点内|绘制期施加：INSTANCE 用实例整数参数 VBO（UV1/UV2，divisor=1），SECTION 用独立 4 B/顶点 UV2 流，纯光照变化只更新该流（`SimpleBedrockModel` 2.6.2 `docs/mesh/README.md` 已确认，不再是推断）|烘焙把 light 写进顶点（[方案 B](./scheme-b-baked-mesh.md)）|**差异点，见 V2**|
|6|缓存失效|每帧重建|资源世代号 + 槽位 `revision`（变换）与 `appearanceRevision`（外观）分离|每帧重建|B1 的失效设计|
|7|上传时机|同步|捕获 / 上传按帧配额摊平（推断）|同步|B1|
|8|LOD|物品按距离|物品 + 展示方块都按距离，含 LOD 资源|物品 / 配件已按距离切 LOD（`GUN_LOD_RENDER_DISTANCE`），展示方块无 LOD 资源|D|
|9|第一人称|即时遍历|**无变化**|B1-b 的目标场景|**不重合**|
|10|26.2+ 延迟渲染|—|无该平台，库内无对应适配|方案的硬约束|**不重合**|
|11|非渲染项|—|枪包同步 GZIP + 256 KB 分片；JEI 一次遍历产出三向查询；弹量统计缓存；客户端资源后台预热|—|与渲染方案无关|

## 待验证点

每条验证只回答一个问题，判定以场景帧时间 + 探针为准，不以「参照实现这么做」为准。

|ID|差异点|要回答的问题|验证手段|阶段|状态|
|---|---|---|---|---|---|
|V1|单枪 draw 数|整枪按材质合并后，满配单枪是否能从 9 次 draw 降到约 2–4 次？（参照实测 ≈0.027 ms/枪；本项仅作对照）|B1-a 实现时加「单枪 draw / 材质数」探针，重跑 multi 满配|B1-a|**部分**：满配 9 次/枪、7.8 µs/draw（[`b1-a-5`](../benchmark/26.35.11.1-4/b1-a-5/测试数据计算报告.md)）；合并到 2–4 次属 B2，未做|
|V2|光与几何解耦|light 烘进顶点（当前设想）与绘制期施加相比，在变光场景下的重建次数与帧时间差多少？|昼夜 / 火把开关 / 手持光源三组场景，记录重建次数与帧时间|B1-a|**已验证**：每跨一次亮度边界重建一次（2.6–2.9 次/秒），单次 0.60 / 1.38 ms ≈ 重构前的单帧成本，光影下 2.74 / 9.10 ms；平均占 0.4%–2.6%，尖峰落在 0.1% low（无光影）与 1% low（满配+光影）（[`b1-b-3`](../benchmark/26.35.11.1-5/b1-b-3/测试数据计算报告.md)）。参照实现的做法已由源码确认（参数 VBO / 独立 UV2 流，键不含 light），本项「是否必需」的答案是**否**：CGC 用持久 VBO 换零上传，代价是变光帧重建，实测平均 0.4%–2.6%、不值得改整套光照路径|
|V3|缓存容量与回收|128 条 / 256 MB / 300 s 的容量模型对满配枪（顶点量为参照场景的 3.2 倍）是否成立？|记录常驻字节/枪、命中率、重建次数；写明失效条件|B1-a|**部分**：CGC 采用 128 条 / 32 MiB、无空闲回收；静态与第一人称稳态 0 重建；常驻字节 / 命中率未采集；B1-b 的分块网格按模型持有，不走该 LRU|
|V4|合批下限|跨实例合批在本场景能到多少次 draw？|TODO 已列的「全场景不同 `RenderType` 去重计数」|B2|**已验证**：`Distinct RenderTypes = 6`（[`b1-a-5`](../benchmark/26.35.11.1-4/b1-a-5/测试数据计算报告.md)）|
|V5|变换 / 外观分离|旋转与位移只换矩阵、不重捕几何，是否等价于方案 B 的「姿态指纹」键？|旋转 / 位移 / 换配件 / 换弹四类操作各测重建次数|B1-a|**已验证**：换弹 3 次 `Bake rebuilds = 0`、变换只换绘制矩阵（[`b1-b-1`](../benchmark/26.35.11.1-5/b1-b-1/测试数据计算报告.md)）；换配件仍会重烘|
|V6|光影下自绘|无光影走持久 VBO、有光影退回 `putBulkData` 的双路径是否必需？（参照实现中未发现光影探测）|开 / 关光影 A/B：画面 + 帧时间|B1 全程、26.3|**已验证（第一人称画面待人工）**：持久 VBO 在光影下可直接绘制，不需要 `putBulkData` 退回；multi 23.9 → 7.19 ms（[`26.35.11.1-4`](../benchmark/26.35.11.1-4/测试数据计算报告.md)），第一人称满配 7.52 → 7.00 ms（[`b1-b-2`](../benchmark/26.35.11.1-5/b1-b-2/测试数据计算报告.md)）|
|V7|静态路径的功能节点|烘焙路径放弃瞄具玻璃 / 模板 / 激光 / 火焰是否可接受？|人工验收清单：展示框 / 掉落物 / 第三人称逐项比对|B1-a|**已验证**：B1-a 人工验收清单通过（[`b1a-static-bake`](./b1a-static-bake.md)）；B1-b 的瞄具模板走烘焙重放|
|V8|分帧预算|捕获 / 上传配额会否把成本推到首帧与换枪帧？|记录首帧、换枪帧、资源重载后的尖峰|B1-a|**部分**：同步烘焙（不做分帧配额），成本落在首次渲染的那几帧，单次 0.1–1.3 ms；首帧 / 换枪帧的尖峰未系统计量|
|V9|LOD 默认值|按距离切 LOD（含「0 = 恒用远景模型」）的收益与画面代价是否值得引入？|同场景远近两档，画面 + 帧时间|D 评估时|**未验证**：CGC 已有物品 / 配件 LOD，本项应改为「默认距离是否该抬高」（B1/B1-b 后每枪成本已很低），而不是引入或删除|

## 数据边界

- `26.35.11.1` / `-2` / `-3` 的全部实测值保持原样，本文只引用、不修订；`tacz1 → tacz2` 的负收益按原报告口径记录为「原因未明」。
- ≈0.027 ms/枪 来自**原版物品展示框**（`26.35.11.1-4`，同场景 4 次；空展示框基线跨端近似），不覆盖 1.2.0 新增展示方块的 section 合批——后者没有任何数据。
- 平台不同（Forge 1.20.1 vs NeoForge 26.3），跨端数字不可直接相减；同平台只比较 `cgc1` 与 `tacz1`。

## 使用方式

- 状态列随批次回填；数值以各 benchmark 报告为准，本文只给判定与链接。
- V1–V9 均已有结论：**V2** 随 `b1-b-3` 验证完毕；**V1** 待 B2 合并；**V3 / V8** 低优先；**V9** 留 D 阶段。
- **26.3 阶段**重新读 V6：本表的结论只来自 1.20.1，延迟渲染下的自绘路径不同。
- 任何一条验证通过都只说明「在该场景、该平台成立」，不自动升级为方案；要写进方案须回到 `Home.md` 的验收与风险登记。
