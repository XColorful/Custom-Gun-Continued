# 方案 D：提交次数削减、LOD 与并行

> 这一组方案都不改变「一次提交要花多少」，只改变「有多少次提交」或「谁来算」。它们单独使用无法达到目标，价值在于给 [方案 B](./scheme-b-baked-mesh.md) 提供乘数或兜底。本文也记录**不采用**多线程的理由。

## D1 可见性与距离剔除

现状（1.20.1 源码可证）：

- 原版实体循环在调用渲染器之前已经做了两层剔除：`LevelRenderer.java:1198` 调用 `EntityRenderDispatcher.shouldRender` → `EntityRenderer.shouldRender` 按实体包围盒（inflate 0.5）做 `frustum.isVisible`；`Entity.shouldRender` 另有 64 × 包围盒的距离判定。展示框、掉落物都是实体，**屏幕外或过远的展示框不会进入 CGC**。
- 方块实体另有一次 `frustum.isVisible`（`LevelRenderer.java:1239`），与枪无关。
- `renderByItem` 的入参只有 `ItemStack / context / PoseStack / buffers / light / overlay`（`GunItemRenderer.java:408-412`），拿不到实体，因此 CGC 无法再做一层实体级剔除。
- CGC 侧可加的只有「实体在视锥内、但枪本身太小」这类阈值。

|手段|收益|代价|
|---|---|---|
|按屏幕投影尺寸跳过低价值模型|视距离与 FOV；multi 测试里 9 把都在近处，收益≈0|需要投影与误差容忍|
|距离阈值（现有 LOD 的变体）|只减少顶点，不减少提交|已有，且不解决大头|

结论：**剔除不是这次重构的收益来源**。原版已经把视锥与距离剔除做完了，CGC 再做的增量接近 0。它的作用是在大世界 / 远距离场景里避免线性恶化，应当保留为「乘数保护」，不投入主要精力。

## D2 LOD

`ClientRenderDistance.shouldRenderLod`（`ClientRenderDistance.java:13-24`）按 `PoseStack` 平移量的平方与 `RenderConfig.GUN_LOD_RENDER_DISTANCE` 比较；屏幕打开任一 GUI 时强制高模；第一人称完全绕过。

- LOD 只替换模型，**提交次数、flush 次数、模板窗口次数都不变**（[场景差异](../chain/scenes-and-static.md#lod-的作用边界)）。
- 在 B 之后的新成本模型里，主变量是 draw 数与重建次数；LOD 减少的顶点只影响「重建一次的代价」和 GPU 顶点吞吐，两者都不是瓶颈。
- multi 基准把低模距离设为 5、枪在 3 格内，9 把全部走高模，说明测试场景没有吃到 LOD。

结论：LOD 保留为远距离场景的降级手段，**不作为重构目标**；也不应为了 LOD 增加缓存键的维度。

## D3 GUI 与 Tooltip

槽位 / tooltip 只画 `SlotModel` 贴图，不进 `ModelObject.render`；单次约 0.0030 ms（`GUI slot icon` 探针）。物品栏里每个可见槽位每帧各调一次，36 格约 0.1 ms（推算），仍不是主要成本。没有优化价值。

## D4 多线程顶点生成

### 事实

- 渲染线程只有一条，顶点生成全部串行；i5-9400F 为 6 核 6 线程，持枪 / multi 时其余核心空闲。
- 每把枪的几何生成彼此独立，共享的是资源实例与缓冲源；`BufferBuilder` / `MultiBufferSource` 不是线程安全的。
- 26.2+ 的 flush 回调在渲染线程上顺序执行，多线程只能加速「回调内部的顶点写入」，仍需在渲染线程汇合。

### 为什么不做

|理由|说明|
|---|---|
|与 B 冲突|B 之后静态场景的顶点生成为 0，没有可并行的负载；动态部分（第一人称脏子树）只占一小块|
|同步开销|渲染线程必须等待全部 worker，收益受最慢分片限制；每帧几十微秒的任务不适合 fork-join|
|内存带宽|10 把枪 ≈ 3.5 MB/帧的顶点写入，已经接近单核的写带宽上限，多核并行会在内存总线上互相争抢|
|风险|缓冲源、状态机、模型实例都是共享可变状态；一旦有遗漏就是随机画面错误|

### 如果将来仍要做

只应作为「B 无法覆盖的动态残留」的兜底：每实例私有缓冲（避免共享 `BufferBuilder`）、按实例分片、渲染线程汇合后按纹理合并。预期把第一人称动态部分的遍历从 0.09 ms 降到 0.05 ms 量级（推算），收益不足以抵消复杂度。

## 定量边界

以 multi 实测为锚：帧时间 5.449 ms、CGC 4.146 ms、场景基线 0.852 ms（实测）。把「可见比例 / 提交成本」作为变量做敏感性分析（`帧时间 = 0.852 + 4.597 × f`，推算）：

|假设|multi 帧时间|说明|
|---|---:|---|
|现状（f = 1）|5.45 ms|实测|
|只合并 flush（理论全免）|4.66 ms|上界；显式 `endBatch` 合计 0.794 ms|
|只合并 flush（上传主导）|4.7–5.0 ms|更接近现实|
|半数可见（f = 0.5）|3.15 ms|剔除能拿到的最好情况之一|
|全部剔除（f = 0）|0.85 ms|**不可达**：枪还在画，仍要付 draw|
|LOD 立方体减半|≈4.2 ms|只减顶点；配件与 draw 不变|
|TaCZ 静态化参照（0.039 ms/枪）|≈1.2 ms|接近但达不到 1.0，且不改善第一人称|

结论：这条路线最多把 multi 从 5.45 压到约 3.1 ms，触不到 1.0 ms 的目标；对第一人称（本来就是 1 次提交）收益为 0。要接近上限，只能做「每次提交的几何复用」，与提交次数正交。

## 汇总

|手段|解决大头|成本模型|建议|
|---|---|---|---|
|视锥 / 距离剔除|否|不变|保留现状，不投入|
|LOD|否|不变|保留，不作为重构目标|
|GUI|否|—|不动|
|多线程|部分（并行度）|不变|**不实施**；B 之后无足够负载|

真正的「提交次数削减」不是把枪剔除掉，而是让同款枪共享几何与 draw——这属于 [方案 B2](./scheme-b-baked-mesh.md#b2静态实例的世界空间合并) 与 [方案 C](./scheme-c-draw-batching.md)。
