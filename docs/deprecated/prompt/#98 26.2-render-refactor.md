Found it — a documented 26.2 pitfall: `RenderPipeline#toBuilder()` doesn't restore the color-target count, so the derived pipeline falls back to `ColorTargetState.DEFAULT`. That re-enables color writes on the `no_color_write` stencil passes (the ocular stencil pass paints its black texture), and drops translucency.

The project's own `NeoStencilOperator` documents this exact pitfall. Compiling the fix:

## 定位：派生烘焙管线丢了颜色目标，瞄具遮罩的「只写模板」失效

日志里没有崩溃；`cgccshader` 已装、22:11:34 关光影、22:12:10 又开回 Complementary。黑目镜只在**关光影**下出现，原因是这次为修「法线/雾」给烘焙网格加的那条派生管线。

**机制**

瞄具模板依赖 `_AttachmentModelRender#renderOcularStencil` 里的 `_colorMask(false,false,false,false)` + `_depthMask(false)` + stencil REPLACE —— 即把目镜几何**只写进模板缓冲、不写颜色**（NeoForge 侧表现为 `no_color_write` 管线修饰器）。这段几何现在是烘焙路径，用的是我派生的 `cgc_baked_entity` 管线。

而 `RenderPipeline#toBuilder()` 有个 26.2 的坑（`b1a` 的「26.2 API 差异」里本来就记着）：**它只拷贝颜色目标数组，不还原 `activeColorTargetStateCount`**，于是 `build()` 落回 `ColorTargetState.DEFAULT`（WRITE_ALL、无混合）：

- `no_color_write` → 丢失，本该只写模板的目镜几何开始写颜色 → 目镜自带的黑色直接盖住场景；
- 半透明混合 → 一并丢失（这就是为什么"准心能看到"——准心是另一段几何）。

项目里 `NeoStencilOperator` 早就在同一个坑上写了注释，这次是派生烘焙管线自己踩到了。

**改法**（[ClientRenderRegistry.java:160](core/src/main/java/dev/xcolorful/customgun/client/init/registry/ClientRenderRegistry.java:160)）：派生时把调用方管线的颜色目标逐个 `withColorTargetState(i, ...)` 重放，其余状态 `toBuilder()` 本来就完整（深度、模板、剔除、顶点格式、define、Iris 映射）。

## 结论：26.2 那种「空提交」在 1.20.1–26.1.2 并不存在，但有一个轻量版可以补

**为什么 26.2 的处理不能直接搬**

26.2 的开销是每个空块每帧仍要走一次 `submitCustomGeometry`，进而触发原版 `RenderTypeFeatureRenderer.prepareGroup` 里的一次 `prepare()`（纹理解析 + UBO 写入），所以空块与真实绘制一样贵。

1.20.1–26.1.2 是即时路径，没有提交队列：[BakedMesh.java:547](../Custom-Gun-Continued/core/src/main/java/dev/xcolorful/customgun/client/model/bake/BakedMesh.java:547) 的 `draw()` 在 `vertexBuffer == null` 处直接 `return true`，既不会 `setupRenderState`，也不 bind / draw。**这部分已经天然省掉了**。

**仍然存在的同类浪费**

第一人称分块循环 [ModelObject.java:782](../Custom-Gun-Continued/core/src/main/java/dev/xcolorful/customgun/client/model/ModelObject.java:782) 对每个可见块都做：

1. `new Cgc$MeshKey(...)` + 两次 Map 查询（`cgc$getOrBake`）；
2. `cgc$chunkPose(...)` → `new PoseStack()` + `invert().transpose()` + 每个路径节点一次 `translate_rotate_scale`（[ModelObject.java:909](../Custom-Gun-Continued/core/src/main/java/dev/xcolorful/customgun/client/model/ModelObject.java:909)）；
3. 然后才进 `drawMesh`，空网格在这里立刻返回。

26.3 的采样结构是「16 个非空 + 9 个空」，1.20.1 是同一套分块逻辑，所以每帧大约有 9 次纯浪费的 PoseStack 分配和路径矩阵乘。量不大（预计 <10 µs），但零画面风险。

**可补的改法**（`cgc$drawChunks`，1.20.1–26.1.2 的活动分支，约 4 行）：

```java
BakedMesh mesh = this.cgc$getOrBake(chunk, renderType, light, overlay,
        red, green, blue, alpha);

// 空块：没有几何可画，姿态计算与绘制都可以省（26.2 的 drawMesh26_2 同样在提交前跳过）
if (mesh.bytes() == 0) {
    drawnAny = true;
    continue;
}
```

用 `bytes() == 0` 而不是新加 `isEmpty()`，是因为后者要按版本分支（1.20.1 与 1.21.6+ 的字段不同），而 `drawOrBake` 里已经在用 `mesh.bytes() > 0` 做同类判断，跨版本都成立。保留 `drawnAny = true` 是为了与原返回语义完全一致（原来空网格也计为「已画」）。

**顺带说明**

- 现在 1.20.1 的 `Draw calls` 把空块也计入（`drawMesh` 里 `drawn = true` 就 `countDraw()`）；补上后口径与 26.3 一致。1.20.1 的 profiler 没有 `countEmptyDraw`，可以不加。
- 不建议改整模路径和瞄具路径：前者的姿态是 `matrixStack.last().pose()` 引用，后者只有一次 `new Matrix4f`，收益可忽略。
- 这个改动在 [ModelObject.java](../Custom-Gun-Continued/core/src/main/java/dev/xcolorful/customgun/client/model/ModelObject.java) 的活动分支里，向上合并到 26.2/26.3 时不影响那边（那边的活动实现是 `drawMesh26_2`）。
