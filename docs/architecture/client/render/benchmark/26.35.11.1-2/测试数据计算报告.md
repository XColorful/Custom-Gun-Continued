# 测试数据计算报告（CGC 1.20.1 / 26.3 · 扩展探针）

**数据**：本目录 48 个文本 —— 两端（`cgc1` = Forge 1.20.1，`cgc2` = NeoForge 26.3）各 6 次重复：标准 4 步 + multi 2 步，Afterburner 与内置探针各 48 条有效记录。子目录 [`multi-baseline/`](./multi-baseline/) 是同一场景的空枪基线（无手持枪、9 个空展示框），两端各 6 次，结果并入本报告、不另建报告。
**口径**：帧时间 = 1000 / FPS；内置探针为采集窗口内逐帧统计，窗口比 Afterburner 略长（F12 提前开始、延迟结束）。所有「平均」为 6 次重复的均值 ± 1 样本标准差。
**环境**：GTX 1660 SUPER / i5-9400F / 1920×1080 165Hz；1.20.1 用 Embeddium + Oculus，26.3 用 Sodium + Iris，全程不启用光影，详见 [标准.txt](./标准.txt)。
**复现**：`python analyze.py` → 三张总览图；`python analyze_extra.py` → 本批次新增指标的逐区块表。

> **与本批次新增探针的口径差异**：`endBatch upload` / `endBatch draw`、`Draw calls`、`Upload bytes` 统计的是**整帧所有** `BufferUploader` 调用（含世界实体、渲染类型切换触发的隐式 flush），不是仅 CGC 的显式 `endBatch`。CGC 归因值 = 同一端「有枪」−「无枪」的差值；`CGC` 一列仍是原有探针的归因值。两者不可直接相加。

## 3. 新增探针读出的成本结构

### 3.1 上传与 draw 的相对权重

|场景|CGC 上传（ms）|CGC draw（ms）|显式 `flush`（ms）|CGC draw 数|单 draw|
|---|---:|---:|---:|---:|---:|
|第一人称持枪|0.077|0.037|0.106|4|9.3 µs|
|multi 9 展示框|0.535|0.181|0.794|18（26−8）|10.1 µs|
|multi + 手持枪|0.648|0.239|0.958|24.5（32.5−8）|9.8 µs|

- **上传是 flush 的主体**：multi 里上传 0.535 ms、draw 0.181 ms，合计 0.716 ms，占显式 flush 0.794 ms 的 90%。
- **上传带宽**：3.49 MB / 0.535 ms ≈ **6.5 GB/s**；第一人称 0.38 MB / 0.077 ms ≈ 4.9 GB/s。与「0.4 MB/枪、10 GB/s 量级」的推算一致。
- **单次 draw ≈ 10 µs**，在标准与 multi 两个场景里一致。这直接给出烘焙方案的下限：即使顶点生成和上传全部消失，每帧仍要付 `draw 数 × 10 µs`。

### 3.2 分配量

|场景|每帧分配|每枪|
|---|---:|---:|
|第一人称持枪|0.181 MB|—|
|multi 9 展示框|0.906 MB|**0.101 MB**|
|multi + 手持枪|1.008 MB|—|
|26.3 第一人称|0.119 MB|—|
|26.3 multi 9 展示框|0.418 MB|0.046 MB|

每枪的顶点数据约 0.388 MB，而实际分配只有约 0.10 MB（1.20.1）。此前按「每立方体 30 个临时向量」估算的 0.38 MB 分配**没有成立**：JIT 逃逸分析消掉了大部分 `Vector3f` / `Vector4f`，剩下的主要是 `NodeTransform` 与集合。**分配不是瓶颈，也不是重构的主要收益来源。**

### 3.3 静态性与动画覆盖

|场景|`State changes`/帧|`Animation channels`/帧|解读|
|---|---:|---:|---|
|multi 9 展示框|**0.00**|0|展示框里的枪节点状态每帧完全不变|
|第一人称持枪|0.98|12|每帧都变；只有 12 条通道在驱动|
|multi + 手持枪|2.00|12|9 把静态 + 1 把动态|

- **静态展示的几何每帧相同**，这直接验证了烘焙复用的前提：展示框场景的缓存命中率应当是 100%，失效只发生在配件 / 可见性 / 光照变化时。
- 第一人称每帧只有约 12 条动画通道写入节点；但 root 的 bob / 后坐由 `GunRendererAddon` 直接写，不计入通道。分区烘焙时仍应以「root 变换提升为绘制矩阵 + 脏子树」为准。
- 26.3 同口径：静态 multi 的 `State changes` 也是 0，第一人称 0.98。

### 3.4 模板清空

multi 每帧 `Stencil clear` 0.0387 ms（9 把枪各清一次）。占 multi 帧时间不到 1%，但占「烘焙之后剩余 CGC 成本」的很大一块，值得合并为每帧一次。

## 5. GPU 指标的口径与局限

`GPU frame busy` 在三个场景都等于帧时间的 **99.4%–99.8%**（空手 0.835 / 0.840，持枪 1.428 / 1.435，multi 5.178 / 5.187）。

这**不能**解读为「GPU 利用率 99%」。`GL_TIME_ELAPSED` 跨越两次帧事件，测的是 GPU 时间线上第一条到条最后一条命令的跨度；CPU 在帧中间断断续续提交命令时，这个跨度自然等于帧时间。它既可能在 GPU 饱和时出现，也可能在 GPU 大量空等时出现。

因此本批数据**没有**回答「GPU 还有多少余量」。要回答需要：

- 把查询缩小到 CGC 自己的 draw 区间（首枪开始 → 末枪结束），得到 CGC 的 GPU 跨度；
- 或用驱动的 GPU busy 计数器 / RenderDoc 单帧；
- 或做「逐步减少 CGC 工作量、看帧时间何时不再下降」的扫描。

建议下一批次把 `GPU frame busy` 改名为 `GPU frame span`，并增加一个只包住 CGC 提交区间的查询。

## 6. 探针开销

用户观察到 1.20.1 空手开测后帧数从约 1300 掉到约 1100。本批次可量化的部分是：

|步骤|上一批 AF 帧时间|本批 AF 帧时间|差值|
|---|---:|---:|---:|
|1.20.1 空快捷栏|0.8003|0.8624|**+0.062**|
|1.20.1 切槽|0.8271|0.8987|+0.072|
|1.20.1 清空|0.7924|0.8561|+0.064|
|1.20.1 持枪|1.4727|1.4452|−0.028|
|26.3 空快捷栏|0.9909|1.0616|+0.071|
|26.3 切槽|0.9949|1.0662|+0.071|
|26.3 清空|0.9832|1.0704|+0.087|
|26.3 持枪|1.5510|1.6259|+0.075|

- 26.3（没有 upload/draw mixin）与 1.20.1 的多数步骤都多出 **0.06–0.09 ms/帧**，说明开销来自两端共用的新增代码：整帧 GPU 查询（每帧 `glGenQueries` + `glBeginQuery` / `glEndQuery` + 查询可用性轮询）与渲染线程分配采样。
- 1.20.1 持枪是唯一变快的步骤（−0.028 ms），与其余步骤方向相反。它的标准差只有 0.02 ms，不能完全用噪声解释；更可能是上一批持枪段本身的运行状态差异。这里按「异常，不据此下结论」处理。
- 内置探针自身的计时开销（AF 与内置帧时间之差）仍然只有 **+0.003–0.006 ms**，说明开销不在 `nanoTime` 埋点，而在 `enabled` 之后多跑的采样逻辑。
- 影响：空手场景约 7%，multi 约 1.3%。**所有场景内与场景间的相对比较不受影响**；本批次的绝对帧时间比无探针构建高约 0.06–0.09 ms。
- 若要继续压低：把 GPU 查询与分配采样改为每 N 帧一次（例如 8 帧），或用 fence 代替 `GL_QUERY_RESULT_AVAILABLE` 轮询。下批次再测时应先做这个改动。
- 用户在现场通过游戏内 FPS 读数观察到空手约 1300 → 1100（约 200 FPS），比 AF 跨批次对照得到的 0.06–0.09 ms 更大。两者口径不同（游戏内读数没有逐帧对齐，且 F3 / 界面状态会影响帧率），**待下次在同一会话内做「F12 开 / 关」A/B 才能定论**。

## 7. 结论

1. **几何遍历仍是最大单项**：标准持枪 0.289 / 0.507 = 57%；multi 3.179 / 4.146 = 77%。
2. **flush 的主体是上传**：multi 里上传 0.535 ms、draw 0.181 ms；单位成本分别为 6.5 GB/s 与约 10 µs/draw。持久 VBO 能去掉上传，但去不掉 draw——draw 数决定烘焙后的下限。
3. **分配不是问题**：每枪约 0.10 MB，逃逸分析已经消掉大部分临时向量。以「减少分配」为目的的微优化收益有限。
4. **静态展示确实每帧相同**：`State changes` 为 0，烘焙缓存的前提成立；第一人称每帧 1–2 次变化、12 条活跃通道，适合「root 矩阵 + 脏子树」。
5. **模板清空在 multi 下合计 0.039 ms/帧**：烘焙之后它会变成剩余成本里显眼的一项，应改为每帧最多清一次。
6. **烘焙后的量级**（推算）：
   - multi：B1（持久 VBO、仍逐枪 draw）≈ 0.85 + 0.18（draw）+ 0.07（快照/状态/模板）≈ **1.2 ms**；B2（按纹理合并 draw）≈ **0.95–1.0 ms**。
   - 第一人称：去掉遍历与上传后约 0.25 ms CGC（残留 draw、delegate、状态），帧时间约 **1.1 ms**；要达到 0.95 ms 还需要处理 delegate 与手部。
7. **本批次没有回答 GPU 余量**：整帧查询测的是命令跨度，不是利用率，需按第 5 节改造后再测。
8. **探针开销 0.06–0.09 ms/帧**，主要来自整帧 GPU 查询与分配采样；对 multi 结论影响可忽略，对空手/标准场景的绝对值有约 7% 的影响。

## 8. 异常与说明

- `multi-baseline/` 使用 `customgun-26.11.35.1` 构建（未含本批次探针），且未装 `cgccpackloader`；基线场景没有枪，也不开 F12，因此与本批次可比。
- 1.20.1 multi 的 `Draw calls` 在 6 次里有 31/34 两种取值（均值 32.5），对应手持枪是否触发额外的缓冲批次；`Upload bytes` 稳定在 3.88 MB。
- `endBatch upload` / `endBatch draw` 是整帧统计，可能超过 `endBatch flush`（后者只包 CGC 的显式 `endBatch` 调用）：例如标准持枪上传 0.109 + draw 0.089 > flush 0.106，因为前者还包含渲染类型切换触发的隐式 flush、手部与入口 flush。
- 1.20.1 的 `Geometry traverse` 在 multi 6 次之间标准差较大（0.235 ms），与 GPU/CPU 频率波动有关；per-gun 数值只作量级使用。
- 26.3 的 `Draw calls` / `Upload bytes` / upload-draw 拆分未实现，留待自定义 FeatureRenderer 阶段。
