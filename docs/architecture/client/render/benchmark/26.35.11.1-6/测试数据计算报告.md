# 测试数据计算报告（CGC 1.20.1 · 26.35.11.1-6 / b1-c-b：B1-c-B 光照原地改写）

**数据**：`b1-c-b/` 下 5 次独立启动，每次含 Afterburner 与 F12 两段，时间不重叠；测试流程见 [`b1-c-b/标准.txt`](./b1-c-b/标准.txt)，与 `26.35.11.1-5/b1-b-3` 相同。
- `cgc1 (N).txt`：Afterburner 7 步 = 空手（夜晚静止）/ ak47 移动 / ak47+光影 静止 / ak47+光影 移动 / 满配 移动 / 满配+光影 静止 / 满配+光影 移动
- `cgc1-builtin (N).txt`：F12 4 段 = ak47 移动 / ak47+光影 移动 / 满配 移动 / 满配+光影 移动
- 第 1–4 次为本批原始采集（无新增探针）；**第 5 次是加定位探针后的复测**，F12 报告多出 `Light update` 与 8 个计数器。第 1、2 节为 n=5，第 3、4 节的新字段只有第 5 次（n=1）。

**改动**：B1-c-B（见 [光照解耦](../../refactor/lighting-decoupling.md)）——第一人称分块网格不再按光照建键，烘焙后留一份 CPU 副本，光照变化时原地改写 uv2 并重传原 VBO；每个键保留主 / 阴影 2 份光照变体。
**场景**：夜晚、脚下火把、按 W 走 8 格后传送回起点、再走 16 格；移动时每跨一格方块光 −1。
**口径**：帧时间 = 1000 / FPS；均值 ± 1 样本标准差。`Static bake` 是**命中帧内所有烘焙之和**，不是单次烘焙；单次光照变化字节 = 每帧平均字节 ÷ 命中帧比例。手动起停误差 ≤0.5–1 s。
**复现**：`python analyze.py`。

## 3. 剩余重建的定位：整模静态路径（第 5 次复测，n=1）

第 5 次的 8 个计数器把成因定死了：

|字段|满配+光影 移动|
|---|---:|
|`Bake rebuilds`|0.070 / 帧|
|`Bake: new key` / `light fill` / `patch failed` / `chunk invalid`|**全 0**|
|差额 = 整模静态路径的烘焙|**0.070 / 帧（100%）**|
|`Light patches`|0.110 / 帧（≈16 次/秒）|
|`Light patch bytes`|31 175.9 B/帧（每次 ≈283 KB）|
|`Light update`|0.412 ms（按 2.2% 命中帧、每帧约 5 次改写折算 ≈82 µs/次）|
|`Light patch: no copy` / `no vbo`|全 0|

- **第一人称分块路径已经干净**：光照变化的四个烘焙成因全是 0，全部走原地改写；按每个光照变化约 5.5 个网格计，一次变化 ≈0.45 ms 改写 + ≈1.6 MB 重传（旧的一次是 9.2 ms + 1.73 MB 顶点发射）。
- 剩下的 0.07 次/帧（每次事件 8.8 块、921 KB、4.4 ms emit）**全部来自整模静态路径**——即第一人称瞄具模板 / 目镜环 / 分划这类经 `_AttachmentModelRender.renderModelPart` → `StaticBake.drawOrBake` 绘制的子网格。这条路径仍把 `light` 放在缓存键里（多展示实例共享同一份网格，不能直接套用「最久未用就改写」），所以亮度一跨格就整段重烘。
- 只在满配+光影出现：无光影时这三段的 `Static bake` 没有任何命中，说明这些子网格没有进烘焙缓存，推测是状态段里由 functional 回调直接发射几何、只能走即时管线。
- 结论：**残留不是改写机制的问题，而是覆盖面没铺到**。给 `renderModelPart` 这条第一人称专用（单实例）路径补上同一套原地改写即可，预期每次事件再省 4.4 ms、`Bake rebuilds` 归零、满配+光影的 1% low 回到静止值附近。

## 4. 与方案 A 的对比

- A 只在「上传」上更省：一次光照变化的重传从「整段交错缓冲」降到 4 B/顶点（满配约 133 KB），即每次事件少传约 1.6 MB。**收益是固定的毫秒级绝对量，与场景帧时间无关**：按本批实测的上传速率（1.73 MB / 0.494 ms）折合约 0.3–0.45 ms/次。
- **不能用「占平均帧时间的百分比」衡量 A**：本批是 145 FPS、枪几乎占满整帧的合成场景；上线场景里枪的比例会下降、帧时间会变长，同一个固定毫秒换算成的百分比会随之变小。取舍应按「单次光照变化的绝对开销」和「它是否仍能把某些帧推过预算」来判断，见[固定毫秒开销在不同帧率下的分量](../../refactor/lighting-decoupling.md#固定毫秒开销在不同帧率下的分量)。
- 本批 B 的实测收益：每次事件 9.246 → 5.149 ms，重建字节 −79%，1% low +65%。剩余成本的 92% 是 emit，A 不改变它，所以 A 也消不掉现在的残留尖峰。
- 因此 A 的定位不变：后续降低上传 / 显存 / 缓存键的优化，不是本阶段掉帧的解法。

## 5. 实机观察对照

- 观察：m4（满配）光影下仍有周期性 low，幅度与上一批 ak47 光影的 low 波动相当、比上一批满配光影小；同一段路第二次走时帧率曲线非常平。
- 数据吻合：单次成本 9.2 → 5.1 ms（约减半）、频率 2.9 → 1.16 次/秒，所以「仍有、但更小更稀」；6.87 ms 的帧塞不下 5.1 ms 的重建，p99 仍在 10.9 ms，所以肉眼仍可见。ak47 光影现在是 0 次重建（旧 2.8 次/秒、单次 2.7 ms），对应「只剩偶发小波动」。
- 「第二次走变平」：第 5 次的计数器显示分块路径已经完全走改写，第二遍几乎没有开销；剩下的静态路径重建与「第几遍」无关（它按光照值建键），如果第二遍看不到 low，说明那一趟这些子网格没被重绘（例如瞄具模板在该视角下没有被绘制）。

## 6. 结论

1. **B1-c-B 按预期消掉了第一人称分块网格的全部光照尖峰**：无光影与 ak47+光影的重建次数归零；满配+光影重建字节 −79%，单次成本 −44%，1% low 59.1 → 97.5、0.1% low 41.1 → 58.0。分块路径的收益已经量化：每次光照变化约 0.4 ms 改写 + 1.4 MB 重传。
2. **剩余重建已定位**：100% 来自整模静态路径（第一人称瞄具模板等子网格，仍按光照建键），每次事件 8.8 块 / 921 KB / 4.4 ms。补上这条路径的原地改写即可收尾。
3. **展示框 / 第三人称的整模静态路径**（同一份网格被多个实例共享）依旧按光照建键，留给 B2 按实例布局处理。
4. 方案 A 的收益是每次事件固定的 0.3–0.45 ms，与场景帧时间无关，也不消除剩余的 emit 尖峰；维持「A 作为后续上传优化」的定位。
