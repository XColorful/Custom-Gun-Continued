两个批次的分工：

- `26.35.11.1` 回答**端间对比**——TaCZ 与 CGC、Forge 与 NeoForge、是否装加速渲染，以及 multi 场景下静态展示优化的差距。
- `26.35.11.1-1` 回答**内部构成与跨版本对照**——两端一次提交的 0.2–0.6 ms 花在哪一层；Afterburner 与内置探针同表对照，并给出探针开销与延迟渲染的差异。
- `26.35.11.1-1` 的 multi 数据采集于附加弹匣泄漏修复前（[报告 5.1](./26.35.11.1-1/测试数据计算报告.md)）。修复后的补充采集在同目录的 [`#91 additional-magazine-fix/`](./26.35.11.1-1/%2391%20additional-magazine-fix/)：两端各 2 次、只测 multi 场景中进游戏空手这一段，四次均为 4005 立方体/帧。此后的构建均包含该修复。
- `26.35.11.1-2` 回答**驱动侧与新的成本量纲**：一次 `endBatch` 里上传与 draw 各占多少、draw 次数与上传字节、渲染线程每帧分配、GPU 是否饱和。multi 的场景基线（9 个石头 + 9 个空展示框、无手持枪）已单独测在 [`multi-baseline/`](./26.35.11.1-2/multi-baseline/)：1.20.1 1174.3 ± 23.9 FPS（0.852 ms），26.3 901.7 ± 42.8 FPS（1.109 ms），结果并入本批次报告、不另建报告。该批次用目录内的 [`analyze_extra.py`](./26.35.11.1-2/analyze_extra.py) 先看新增指标，标准指标仍按 `26.35.11.1-1/analyze.py` 的口径统计。
  - 注意：本批次新增探针带来约 **0.06–0.09 ms/帧** 的固定开销（26.3 全步骤、1.20.1 除持枪外），空手场景约 7%、multi 约 1.3%；整帧 `GPU frame busy` 实测为帧时间的 99.4%–99.8%，它是 GPU 命令跨度而不是利用率，不能用来判定 GPU 余量。

## 约定

- 每个批次目录自带 `analyze.py`，运行后重新生成该批次的图；报告中的数值均由脚本计算，不手工录入。
- `analyze.py` 同时兼容 1.20.1 与 26.3 的字段名（`Model render total` / `Model submit`、`endBatch flush` / `Model flush`、`endBatch calls` / `Geometry submits`），26.3 批次可按同样方式（6 次重复 × 4 步 + 6 次 × 2 步）采集后直接复用。
- 原始数据中的进程名必须过滤为 `javaw.exe`（Afterburner 会连启动器一起录制；官方启动器在后台未最小化会略微拉低帧数）。
- 内置探针的窗口比 Afterburner 略长（提前开始、延迟结束），对齐方式见各批次报告。
- 探针定义与埋点位置见 [渲染链路分析总览](../chain/Home.md) 的「测量与数据登记」。
- 单次会话的结论不作跨版本外推；跨版本对比只在同一批次内进行。
- 修复（`31c977d1a`）后的 multi 场景可直接用 `Cubes submitted` 判定是否再次泄漏：9 把展示框枪、进游戏空手时为 **4005/帧**（修复前泄漏时为 4554，每把 61）。
