## 修复方向（未动代码）

和 `_renderScope` / `_renderHand` 同一套：给文字节点缓存 path（`ModelObject.getPath` 现成，参照 `scopePosPath`），在 **submit 阶段**沿 path 摆位并 `submitText`，`TextRender` 不再依赖 `delegateRender` 和 ThreadLocal。因为 `GunModelObject` 和 `AttachmentModelObject` 都继承 `ModelObject`，放在 `ModelObject.render` 的 submit 段可以一次覆盖两者；同时要把 `setFunctionalRenderer(name, ...)` 那条挂载去掉，否则 flush 期还会跑一遍。

## 性能提升

先给确定的部分（直接由代码决定，不是估算）：

- 瞄具模型每帧的 `ModelObject.render` 调用：**2 → 1**
- 该模型的 buffer 提交/绘制批次：**2 → 1**
- 每帧多做的那一遍：N 个骨骼的遍历、N 次 `NodeTransform.capture`（两个列表）、N 次变换 apply/还原、全部立方体的顶点生成、一次 `endBatch`（上传 + draw call）、delegateRenderers 循环、每个文字节点一次 `drawInBatch`
- 瞄具上的文字绘制：**2 → 1**

绝对数值取决于模型面数（模型是资源包提供的，仓库和本机都没有可数的瞄具资产），按常见规模估：

| 瞄具 | 立方体 | 重复顶点/帧（24 顶点/立方体） |
|---|---|---|
| 小红点 | 30–80 | 0.7k–1.9k |
| ACOG / LPVO | 150–400 | 3.6k–9.6k |

对应 CPU 侧每帧大约省 **0.03–0.3 ms**，即 60 FPS 下 0.2%–2% 的帧时间。GPU 侧的收益要打折：那份重复几何本来就被深度测试整体挡住，主要省下的是顶点变换和一个 draw call，而不是填充率。

所以结论是：**这是一次正确性 + 省重复工作的修复，不是能明显提帧的优化**。它的实际价值在「瞄具模型提交量减半」「文字不再重复绘制」，以及 26.2 上那个可见的双份文字。如果你要一个准确的数字，我可以加一个临时计数器（每次 `super_render` 统计顶点数和纳秒、按帧汇总），你跑一次就能拿到这台机器上的真实值。
